Update PixiJS BitmapText Without Garbage Collection

Updating a PixiJS BitmapText instance dynamically without triggering garbage collection is possible, but not through the standard .text property assignment. In high-frequency rendering loops—such as HUD counters, damage numbers, or timers—setting bitmapText.text = "123" generates garbage by allocating new JavaScript string primitives and triggering internal glyph-tracking churn. To achieve zero-allocation text updates, you must bypass runtime string creation and directly mutate pre-allocated internal glyph sprites or build a dedicated character pool.

Why Standard Updates Trigger Garbage Collection

When you execute bitmapText.text = newString, two distinct memory allocation events occur:

  1. JavaScript String Allocation: Converting numbers or combining characters creates new primitive strings on the V8/JS heap that must eventually be collected.
  2. Internal Structure Rebuilding: PixiJS parses the string, measures kerning, and updates an internal array of child glyph sprites. While PixiJS uses pooling for its glyph sprites, clearing, slicing, or resizing text lengths still creates intermediate object references and array modifications.

Technique 1: Pre-Allocated Glyph Pools

The most reliable way to avoid GC is to avoid the BitmapText class directly for high-frequency dynamic text and instead construct a fixed-size pool of PIXI.Sprite instances mapped to your bitmap font’s textures.

  1. Pre-populate Sprites: Determine the maximum character length required (e.g., 8 characters for a score). Instantiate that fixed number of child sprites under a single PIXI.Container.
  2. Extract Textures Once: Access the cached character textures directly from PIXI.BitmapFont.available[fontName].chars[charCode].texture.
  3. Update Textures via Math: Instead of converting numbers to strings, use arithmetic (modulo and division) to isolate individual digits as integer character codes. Assign these pre-cached textures directly to the corresponding child sprites.
  4. Toggle Visibility: If the value requires fewer characters than the maximum capacity, set sprite.visible = false instead of destroying or unlinking the child.

This method completely bypasses the JavaScript string parser, generates zero runtime allocations, and avoids the internal layout loop of BitmapText.

Technique 2: In-Place Mutation of Internal Glyph Data

If you must use an existing BitmapText instance, you can modify its internal children directly without calling the .text setter:

  1. Initialize to Maximum Width: Instantiate the BitmapText with a placeholder string of maximum expected length (e.g., "000000"). This ensures the underlying sprite array allocates the required capacity upfront.
  2. Direct Glyph Replacement: Access the internal children via bitmapText.children. Loop through the children and reassign their .texture properties using textures looked up directly from BitmapFont.available[fontName].chars[charCode].
  3. Manual Offsets: Update each sprite’s x and y properties based on the character's xOffset, yOffset, and xAdvance data stored in the font definition to preserve correct spacing.
  4. Hide Unused Glyphs: Set .visible = false on remaining sprites when the current text is shorter than the initialized maximum.

Technique 3: Zero-Allocation String Caching

If standard .text updates must be retained for kerning calculations, you can eliminate JavaScript string GC by pre-generating a lookup table for common values.

For counters from 0 to 9999, pre-allocate an array of strings at application startup:

const stringCache = Array.from({ length: 10000 }, (_, i) => i.toString());

Passing stringCache[score] into bitmapText.text eliminates dynamic string allocations. While this does not prevent PixiJS’s internal layout overhead, it removes the primary source of per-frame heap growth in the JavaScript runtime.
