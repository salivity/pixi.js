How PixiJS Chooses WebGPU Over WebGL2 Automatically

Starting in version 8, PixiJS introduces a dual-engine architecture that automatically prioritizes WebGPU while retaining WebGL2 as a reliable fallback. During application initialization, PixiJS inspects the host runtime using an asynchronous feature-detection and priority-ranking pipeline. If the browser and underlying hardware successfully grant access to a modern graphics adapter and device, PixiJS selects the WebGPU renderer; otherwise, it gracefully steps down to WebGL2 without requiring manual intervention from the developer.

The Initialization Pipeline

When you call Application.init() or autoDetectRenderer(), PixiJS queries an internal registry of renderers. Each renderer registers its own priority order and an asynchronous test function designed to evaluate runtime compatibility.

By default, the WebGPURenderer sits at the top of the priority list, followed by the WebGLRenderer. PixiJS iterates sequentially through this list, invoking each renderer's respective test() method until one returns true and initializes successfully.

WebGPU Feature Detection

PixiJS does not simply check for the presence of the global navigator.gpu object. Because the presence of an API stub does not guarantee that hardware acceleration is active or compatible, PixiJS executes a live capability test:

  1. API Availability: PixiJS verifies that navigator.gpu exists in the global scope.
  2. Adapter Request: It attempts to retrieve a graphics adapter by calling navigator.gpu.requestAdapter(). If the system lacks compatible GPU drivers, or if the browser has disabled WebGPU via security flags or blocklists, this call resolves to null.
  3. Device Instantiation: If an adapter is returned, PixiJS attempts to call adapter.requestDevice(). Only when an actual device context is acquired does the test() method resolve positively.

If all three stages pass, PixiJS allocates a WebGPU context and binds it to the canvas.

The WebGL2 Fallback Sequence

If any step of the WebGPU verification fails, catches an error, or times out, PixiJS discards the candidate and advances to the next entry in its renderer list: the WebGLRenderer.

For WebGL2 detection, PixiJS calls canvas.getContext('webgl2'). If the browser successfully returns a WebGL2RenderingContext, PixiJS proceeds with the WebGL2 rendering pipeline. If WebGL2 is also unavailable (due to legacy drivers or browser constraints), PixiJS attempts to fall back to WebGL1 (canvas.getContext('webgl')) before throwing an initialization error.

Overriding the Automatic Behavior

While the automatic selection prefers WebGPU whenever viable, developers can manually influence the priority logic using the preference property within the initialization configuration:

await app.init({
    preference: 'webgpu', // Forces or prioritizes WebGPU
    // preference: 'webgl', // Skips WebGPU probing and prioritizes WebGL2
});

Setting preference: 'webgl' instructs the system to bypass the WebGPU adapter negotiation entirely, instantly selecting the WebGL2 backend. Leaving this field blank or setting it to 'webgpu' ensures the engine will always favor WebGPU whenever the client platform allows it.
