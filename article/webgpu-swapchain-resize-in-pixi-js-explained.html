WebGPU Swapchain Resize in Pixi.js Explained

This article explores how Pixi.js manages swapchain reconfiguration under its WebGPU renderer when a browser window resizes. It covers the transition from CSS layout changes to canvas dimension updates, the reconfiguration of the GPUCanvasContext, the reallocation of associated render targets such as depth and multisample textures, and how the rendering loop synchronizes to prevent frame tearing or invalid presentation states.

The WebGPU Presentation Context and Canvas Sizing

In WebGPU, the presentation mechanism formerly known as the swapchain is managed directly by the GPUCanvasContext. When a browser window resizes, the DOM layout changes, altering the visible bounds of the HTML <canvas> element.

Pixi.js monitors resize events either through an explicit call to renderer.resize(width, height) or automatically via ResizePlugin when using autoDensity and responsive containers. Once detected, Pixi.js recalculates the canvas’s physical drawing buffer dimensions by multiplying the logical CSS dimensions by the window’s resolution (device pixel ratio):

\[\text{Physical Width} = \text{CSS Width} \times \text{Resolution}\] \[\text{Physical Height} = \text{CSS Height} \times \text{Resolution}\]

Assigning these physical dimensions directly to canvas.width and canvas.height signals to the browser engine that the underlying drawing buffer must change size.

Reconfiguring the GPUCanvasContext

When canvas physical dimensions change, the WebGPU specification dictates that the existing swapchain textures are invalidated. Pixi.js handles this through its GpuCanvasContext and render target systems:

  1. Context Update: Modern WebGPU automatically adapts the default drawing buffer textures when the <canvas> element's width and height properties update. However, to guarantee format and usage integrity, Pixi.js re-evaluates the context configuration via: 
    canvasContext.configure({
    device: gpuDevice,
    format: preferredFormat,
    alphaMode: premultiplied ? 'premultiplied' : 'opaque',
    usage: GPUTextureUsage.RENDER_ATTACHMENT | GPUTextureUsage.COPY_SRC
});
  2. Backbuffer Invalidation: Pixi.js marks the current root texture view as dirty. On the subsequent frame, calling context.getCurrentTexture() yields a newly sized GPUTexture matching the updated canvas dimensions.

Recreating Ancillary Render Targets

While the primary color buffer texture is provided directly by the GPUCanvasContext, associated secondary buffers are not created automatically by WebGPU. The Pixi.js GpuRenderTargetSystem detects that the root render target dimensions no longer match the previous frame's configuration and recreates the following auxiliary resources:

  • Multisample Textures (MSAA): If multisampling is enabled (e.g., sample count > 1), Pixi.js destroys the previous transient multisample color texture and allocates a new GPUTexture with matching sample counts and new dimensions.
  • Depth and Stencil Buffers: If the scene utilizes depth testing or masking that requires a depth/stencil attachment, Pixi.js discards the outdated depth-stencil GPUTexture and instantiates a new one to prevent dimension mismatch errors during render pass execution.

Frame Synchronization and Render Pass Execution

WebGPU strictly prohibits executing a GPURenderPassEncoder where the attachments have mismatched dimensions. Pixi.js prevents rendering collisions during resizing through sequential execution:

  1. Resize triggers update the global projection matrix and update the root RenderTarget.
  2. The internal texture system frees old cached textures and allocates the correctly sized ancillary textures before the render pass begins.
  3. At the start of the frame, Pixi.js acquires the new texture via context.getCurrentTexture().createView().
  4. The render pass descriptor binds the current canvas view alongside the newly sized MSAA and depth-stencil views.
  5. The pass executes commands using updated viewport and scissor rectangles corresponding to the new surface dimensions.

By isolating context configuration and ancillary buffer creation inside its centralized render target system, Pixi.js ensures swapchain reconfigurations occur seamlessly between frame boundaries without producing GPU validation errors.
