PixiJS drawElements vs drawArrays Rendering

PixiJS relies on WebGL to render 2D and 3D graphics on the GPU, abstracting low-level commands into intuitive geometry and mesh objects. At the WebGL level, the engine submits geometry to the screen using either drawElements or drawArrays. This article outlines how these two rendering calls differ within PixiJS, examining how vertex indices, memory consumption, GPU cache utilization, and geometry structure dictate which call PixiJS executes.

The Underlying WebGL Distinction

The fundamental difference between drawArrays and drawElements is how the GPU accesses vertex data:

  • drawArrays (Non-Indexed Rendering): Reads vertex attributes sequentially from the bound vertex buffer object (VBO). To draw multiple adjacent triangles, shared vertices must be duplicated in the buffer.
  • drawElements (Indexed Rendering): Uses an additional index buffer (an element array buffer) containing integer pointers. The GPU references this list of indices to pull vertex data from the VBO, allowing individual vertices to be referenced multiple times across different triangles.

How PixiJS Determines the Draw Call

In PixiJS, rendering geometry centers around the Geometry class. The presence of an index buffer determines the draw pipeline used by the renderer:

  1. Indexed Geometry (drawElements): When you add an index buffer via geometry.addIndex(...), PixiJS automatically flags the geometry as indexed. During the render phase, the GeometrySystem binds both the vertex attributes and the element array buffer, subsequently executing gl.drawElements(...).
  2. Non-Indexed Geometry (drawArrays): If no index buffer is supplied, PixiJS reads the geometry purely sequentially. It determines the number of vertices from the attribute lengths and executes gl.drawArrays(...).

Memory Footprint and Redundancy

The choice between indexed and non-indexed geometry heavily impacts memory allocation in PixiJS applications:

  • Memory Overhead with drawArrays: A simple quad composed of two triangles requires 6 distinct vertices. If each vertex holds attributes such as 2D position (8 bytes), UV coordinates (8 bytes), and tint colors (4 bytes), a single quad consumes 120 bytes. Complex geometries with high attribute counts compound this redundancy quickly.
  • Memory Savings with drawElements: The same quad requires only 4 unique vertices (80 bytes) and 6 indices stored as 16-bit integers (Uint16Array, consuming 12 bytes), totaling 92 bytes. For intricate meshes, terrain, or subdivision surfaces, indexed geometry significantly reduces both CPU-to-GPU transfer sizes and VRAM footprint.

GPU Post-Transform Vertex Cache

Modern GPUs contain a post-transform vertex cache that stores the output of recently executed vertex shaders.

When PixiJS uses drawElements, the GPU uses vertex indices to identify previously transformed vertices. If an incoming index matches an entry in the cache, the GPU bypasses the vertex shader entirely for that vertex and reuses the cached output. Because drawArrays lacks explicit vertex IDs, it rarely benefits from this caching behavior, forcing the GPU to re-evaluate the vertex shader for duplicated coordinates.

Impact on PixiJS Batch Rendering

PixiJS’s core performance advantage comes from its BatchRenderer, which aggregates sprites, graphics, and simple meshes into a single draw call.

The batching system relies almost exclusively on drawElements. PixiJS pre-allocates an index buffer containing repeating quad indices ([0, 1, 2, 0, 2, 3], offset by four for each subsequent quad) and fills a dynamic vertex buffer with transformed sprite vertices. This design allows PixiJS to render thousands of independent sprites in a single gl.drawElements call without vertex duplication.

While custom meshes with unique topologies or streaming point-cloud data can leverage drawArrays effectively, structured meshes and standard display objects in PixiJS are designed around drawElements to maximize batching capacity, reduce memory overhead, and leverage hardware-level caching.
