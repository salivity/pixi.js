How PixiJS Handles Window Visibility and Ticker Pausing

PixiJS relies on browser rendering lifecycles and its internal Ticker architecture to manage rendering and computation pauses when a window is minimized or hidden. Rather than continuously querying document state, PixiJS utilizes the native behavior of requestAnimationFrame—which modern browsers automatically suspend when a document is not visible—alongside internal delta time clamping to prevent physics and animation distortions upon reactivation. This article explains how PixiJS works with browser visibility states, how the Ticker pipeline halts calculations, and how timing spikes are mitigated upon return.

The Role of requestAnimationFrame

PixiJS drives its rendering and update loops through the PIXI.Ticker class, which wraps the standard Web API method window.requestAnimationFrame.

Modern web browsers integrate requestAnimationFrame directly with the Page Visibility API. When a tab is backgrounded, minimized, or occluded, the browser automatically suspends or heavily throttles execution of requestAnimationFrame callbacks to conserve CPU, GPU, and battery resources. Because PixiJS relies directly on this cycle to invoke tick updates, the execution of the tick loop stops automatically without requiring PixiJS to manually register low-level visibilitychange event listeners.

The PIXI.Ticker Execution Loop

When app.ticker (or PIXI.Ticker.shared) is running, it recursively schedules frames using an internal loop:

  1. The browser invokes the queued requestAnimationFrame callback.
  2. The Ticker captures the current high-resolution timestamp using performance.now().
  3. It computes the elapsed time (deltaMS) since the previous frame.
  4. It executes registered listener callbacks (such as custom update functions and the main render pass).
  5. It requests the next animation frame.

When the window loses visibility, step 1 is halted by the browser. As a result, subsequent tick calculations and rendering operations immediately enter a dormant state.

Preventing Delta Spikes on Wakeup

A primary technical challenge when resuming a paused application loop is the time discrepancy between the last frame executed before backgrounding and the first frame executed after reactivation. Without mitigation, calculating elapsed time using currentTime - lastTime would produce a massive delta value, causing physics simulations to explode or animations to jump forward erratically.

PixiJS mitigates this behavior inside Ticker.update():

  • Delta Clamping: PixiJS provides a minFPS property on the Ticker instance (defaulting to 10). This sets an upper boundary on the allowed elapsed time per frame calculation. If the calculated deltaMS exceeds the threshold determined by minFPS, PixiJS clamps the delta to that maximum allowed value.
  • Timestamp Normalization: When the browser re-triggers requestAnimationFrame after a visibilitychange event marks the document visible again, PixiJS updates its internal lastTime reference, treating the resume as a fresh step rather than attempting to catch up on missed elapsed frames.

Explicit Pausing via the Page Visibility API

While the implicit pause driven by requestAnimationFrame handles rendering and tick computations, PixiJS also allows developers to implement manual state controls if background tasks must be explicitly frozen. Developers can listen to the native visibilitychange event and interact with the Ticker API directly:

document.addEventListener('visibilitychange', () => {
    if (document.hidden) {
        app.ticker.stop();
    } else {
        app.ticker.start();
    }
});

Using app.ticker.stop() completely cancels any pending animation frame requests and sets the ticker's started flag to false. Calling app.ticker.start() resets the internal timing markers and reschedules the animation frame loop cleanly, ensuring complete control over runtime updates across visibility transitions.
