PixiJS Filter Fragment Shader Coordinate Normalization

This article explains how Pixi.js handles coordinate normalization inside custom filter fragment shaders. Pixi.js processes visual filters by rendering objects to intermediate textures, which requires transforming standard screen-space pixels into normalized texture coordinates ([0.0, 1.0]). Understanding how Pixi.js supplies built-in uniforms such as inputSize, filterArea, and filterClamp ensures that shaders sample textures accurately without distortion, edge bleeding, or resolution mismatches.

The Filter Texture Space

When Pixi.js applies a filter to a display object, it renders that object to an off-screen render texture pooled from its internal memory. Because pooled textures are often larger than the actual display object or the screen viewport, the standard normalized coordinate vTextureCoord spans the entire pooled texture rather than just the bounds of your filtered object.

To calculate accurate effects (such as radial blurs, procedural patterns, or vignette masks), you must distinguish between:

  1. Texture UV space: The normalized [0.0, 1.0] coordinates of the intermediate render buffer.
  2. Normalized filter space: The normalized [0.0, 1.0] coordinates relative strictly to the bounding box of the filtered object.
  3. Screen pixel space: The absolute pixel coordinates on the canvas.

Built-in Uniforms for Coordinate Calculation

Pixi.js automatically injects a set of uniforms into filter fragment shaders to help map between these coordinate spaces:

  • inputSize (vec4): Contains the dimensions of the input render texture.
    • inputSize.xy: Width and height of the input texture in pixels.
    • inputSize.zw: Inverse dimensions (1.0 / width, 1.0 / height).
  • filterArea (vec4): Defines the active filtering region.
    • filterArea.xy: The width and height of the filtered area in pixels.
    • filterArea.zw: The top-left offset (x, y) of the filtered area within the render texture.
  • filterClamp (vec4): Defines the safe UV sampling boundaries (minX, minY, maxX, maxY) to prevent edge-bleeding caused by texture sampling outside the rendered object bounds.

Converting Coordinates in GLSL

1. Converting Normalized Texture UV to Pixel Coordinates

To get the current fragment position in actual pixels, multiply the incoming vTextureCoord by the input resolution:

vec2 pixelCoord = vTextureCoord * inputSize.xy;

2. Normalizing to Local Object Coordinates [0.0, 1.0]

To generate effects that scale strictly with the filtered object—regardless of padding or render texture dimensions—map the pixel position relative to filterArea:

vec2 normalizedCoord = (pixelCoord - filterArea.zw) / filterArea.xy;

In this system:

  • (0.0, 0.0) represents the top-left corner of the filtered object.
  • (1.0, 1.0) represents the bottom-right corner of the filtered object.

3. Converting Normalized Coordinates Back to Texture UVs

If you perform math in normalized filter space (for example, applying UV displacement or wave distortions), you must convert back to texture UV coordinates before sampling uSampler:

vec2 newPixelCoord = (modifiedCoord * filterArea.xy) + filterArea.zw;
vec2 newTextureCoord = newPixelCoord * inputSize.zw;

Preventing Sampling Artifacts with filterClamp

Because pooled textures contain unused background pixels or neighboring draw data, sampling outside the filtered boundary causes visual glitches. When calculating displaced UVs, clamp the final texture coordinates using filterClamp:

vec2 safeCoord = clamp(newTextureCoord, filterClamp.xy, filterClamp.zw);
vec4 color = texture2D(uSampler, safeCoord);

By combining inputSize, filterArea, and filterClamp, Pixi.js ensures fragment shaders can normalize coordinates relative to the object while properly mapping and clamping samples to the underlying WebGL render texture.
