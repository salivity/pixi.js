Pixi.js WebGL vs WebGPU Blend State Descriptors

Pixi.js v8 introduced a unified rendering architecture capable of driving both WebGL and WebGPU backends through a single abstraction layer. A major architectural divergence between these two APIs lies in how blend states are defined and applied: WebGL relies on dynamic, state-machine function calls applied at draw time, whereas WebGPU requires immutable, fully-defined blend state descriptors baked into render pipelines. Understanding these differences highlights how Pixi.js translates high-level blend modes into low-level GPU configurations.

Dynamic State Machine vs. Immutable Pipeline Descriptors

In WebGL, blend states are mutable and tracked dynamically on the global graphics context. Pixi.js manages blend modes in WebGL using its WebGLState system, switching active states on the fly via discrete OpenGL calls:

  • gl.enable(gl.BLEND) / gl.disable(gl.BLEND)
  • gl.blendFuncSeparate(srcRGB, dstRGB, srcAlpha, dstAlpha)
  • gl.blendEquationSeparate(modeRGB, modeAlpha)

These calls modify the immediate execution state of the driver and do not alter the compiled shader program.

In WebGPU, dynamic blend switching during a render pass does not exist. Blend states must be explicitly declared within the GPURenderPipelineDescriptor inside the fragment.targets[i].blend property. Once a GPURenderPipeline is compiled, its blend behavior is completely immutable. Pixi.js must supply a complete GPUBlendState descriptor upfront before issuing any draw calls.

Structural Mapping of Blend Components

The structural representation of blend equations and factors differs significantly across the two backend implementations within the Pixi.js pipeline:

  • WebGL Representation: Pixi.js maps its internal blend modes (such as normal, add, multiply, or screen) to arrays of WebGL integer constants representing factors and equations. When a sprite with a different blend mode is drawn, Pixi.js compares the mode's integer values against the current context cache and executes state transitions only for the differing parameters.
  • WebGPU Representation: Pixi.js translates blend modes into structured JavaScript objects adhering to the GPUBlendState interface. This structure explicitly separates color and alpha calculations into distinct GPUBlendComponent objects:
{
    color: {
        srcFactor: 'src-alpha',
        dstFactor: 'one-minus-src-alpha',
        operation: 'add'
    },
    alpha: {
        srcFactor: 'one',
        dstFactor: 'one-minus-src-alpha',
        operation: 'add'
    }
}

Instead of numeric driver constants, WebGPU blend descriptors strictly use string-based enumerations (GPUBlendFactor and GPUBlendOperation).

Pipeline Caching and Batching Implications

The shift from dynamic execution to declarative descriptors fundamentally changes how Pixi.js caches render state and batches draw commands:

  1. Pipeline Key Generation: Because WebGPU blend state is tied directly to the pipeline, changing a blend mode changes the pipeline itself. Pixi.js incorporates the blend state descriptor into its pipeline cache key (pipelineKey). If a sprite requires a blend mode that has not yet been used with its current shader layout, Pixi.js must compile or retrieve a unique GPURenderPipeline. In WebGL, Pixi.js reuses the same shader program and simply alters driver flags.
  2. Batch Breaking Mechanics: In Pixi.js's batch renderer, geometry sharing identical textures, shaders, and blend modes is batched together. In WebGL, a blend mode change simply flushes the current batch, updates the context state via blendFuncSeparate, and continues drawing with the same program. In WebGPU, a blend mode change forces a pipeline swap via passEncoder.setPipeline(), requiring the renderer to bind an entirely distinct pipeline object compiled with the target blend descriptor.
