PixiJS 16-Bit vs 32-Bit Dynamic Index Buffers

PixiJS relies on dynamic vertex and index buffers to batch and render 2D primitives, sprites, and meshes efficiently. To maximize rendering throughput and minimize memory overhead, PixiJS chooses between 16-bit (Uint16Array) and 32-bit (Uint32Array) index buffers based on hardware capabilities, vertex counts, and batch sizes. While 16-bit indices are the standard default for dynamic batching due to lower bandwidth consumption and universal WebGL compatibility, 32-bit indices are deployed for complex custom meshes and scenes that exceed the 16-bit addressable limit.

Hardware Support and WebGL Limits

In core WebGL 1.0 specifications, index buffers only natively support 8-bit (gl.UNSIGNED_BYTE) and 16-bit (gl.UNSIGNED_SHORT) values. To use 32-bit unsigned integer indices (gl.UNSIGNED_INT), the WebGL context must support and enable the OES_element_index_uint extension. In WebGL 2.0, 32-bit index support is included natively in the core specification.

A 16-bit index can address a maximum of 65,536 vertices (values 0 to 65,535). If a single draw call references more than this number of vertices, 16-bit indexing cannot address them, necessitating either splitting the draw call or upgrading the index buffer to 32-bit.

How the PixiJS BatchRenderer Uses 16-Bit Indices

PixiJS’s internal batching system (BatchRenderer and BatchGeometry) aggressively defaults to 16-bit indices. When rendering sprites, graphics, and simple 2D display objects, PixiJS aggregates multiple distinct objects into a shared dynamic vertex and index buffer to draw them in a single draw call.

The batch renderer presets a maximum batch limit—typically between 2,000 and 4,000 quads per flush. Because a single quad requires four vertices and six indices:

  • 2,000 quads = 8,000 vertices and 12,000 indices.
  • 4,000 quads = 16,000 vertices and 24,000 indices.

Even at peak batch capacities, the vertex count remains well beneath the 65,535 threshold. Consequently, PixiJS pre-allocates index buffers using Uint16Array. The indices are repeatedly filled with standard repeating quad patterns ([0, 1, 2, 0, 2, 3], offset per quad). Because the buffer pattern is static relative to the quad count, PixiJS uploads this 16-bit index buffer once to GPU memory as a STATIC_DRAW buffer or reuses it dynamically without needing 32-bit pointers.

Memory Footprint and Bus Bandwidth

Dynamic batching requires pushing modified vertex data to the GPU each frame. Index data for dynamic batches can also require updates when draw configurations change.

  • 16-bit indices: 2 bytes per index element.
  • 32-bit indices: 4 bytes per index element.

Using 16-bit indices cuts index buffer memory usage and bus transfer bandwidth in half. In high-performance 2D rendering, reducing GPU bus traffic directly improves frame stability, lowers cache misses on the GPU vertex fetcher, and reduces mobile device memory consumption.

Switching to 32-Bit Indices for Custom Meshes

When working outside the standard BatchRenderer—such as with PIXI.Mesh, custom PIXI.Geometry, or third-party spine/skeletal animations—vertex data is not constrained to small quad batches.

When a custom geometry's vertex buffer exceeds 65,535 elements:

  1. Index Buffer Selection: PixiJS requires an index buffer populated by a Uint32Array.
  2. Context Capability Check: The renderer checks whether WebGL 2 is active or if OES_element_index_uint is available in WebGL 1. If supported, the buffer binds using gl.UNSIGNED_INT during the gl.drawElements call.
  3. Fallback: If 32-bit indexing is unsupported by the context, geometries that exceed 65,535 vertices fail to render properly unless manually partitioned into smaller meshes.

Dynamic Buffer Allocation and Sizing

In dynamic mesh scenarios where geometry vertices are added or removed at runtime, PixiJS's Buffer class manages underlying typed arrays. If an index buffer starts as a Uint16Array and expands dynamically past the 65,535 threshold, the buffer must be reconstructed as a Uint32Array.

Because swapping from 16-bit to 32-bit typed arrays requires reallocating WebGL buffer storage via gl.bufferData, PixiJS designs the standard pipeline to flush batches before crossing the 16-bit threshold. This architectural design ensures that dynamic sprite batching stays permanently on the fast, 16-bit memory path, reserving 32-bit overhead strictly for complex, explicit geometries.
