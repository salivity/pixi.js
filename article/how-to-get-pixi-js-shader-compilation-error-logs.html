How to Get Pixi.js Shader Compilation Error Logs

When developing custom shaders in Pixi.js, syntax mistakes or driver incompatibilities will cause the underlying WebGL program to fail during compilation. While Pixi.js surfaces these issues in the developer console by default, extracting compilation error logs programmatically requires interacting with the renderer's WebGL context or intercepting the engine's compilation routine. This guide outlines how Pixi.js handles shader errors and how to extract raw compilation logs directly for custom debugging, automated testing, or user-facing error reporting.

Default Error Behavior in Pixi.js

When you create a shader using PIXI.Shader.from() or PIXI.Program.from() (or the equivalent API in PixiJS v8), the engine delays compilation until the first render pass where the shader is drawn.

If compilation fails, Pixi.js calls gl.getShaderInfoLog() internally and outputs an error to console.error. The output typically includes:

  • The specific line and column where the compilation failed.
  • The error description returned by the graphics driver.
  • The shader source code prepended with line numbers for inspection.

If you only need to read the errors during local development, opening your browser's developer tools will display this diagnostic output automatically.

Extracting Logs Programmatically via WebGL

If you need to intercept and handle the error string programmatically before applying the shader to a scene, you can validate the GLSL strings directly against the renderer's active WebGL context.

Here is a standalone helper function to compile and extract logs safely:

function validateShader(renderer, vertexSrc, fragmentSrc) {
    const gl = renderer.gl;

    function compile(type, source) {
        const shader = gl.createShader(type);
        gl.shaderSource(shader, source);
        gl.compileShader(shader);

        const success = gl.getShaderParameter(shader, gl.COMPILE_STATUS);
        if (!success) {
            const infoLog = gl.getShaderInfoLog(shader);
            gl.deleteShader(shader);
            return { success: false, log: infoLog };
        }

        return { success: true, shader };
    }

    const vertResult = compile(gl.VERTEX_SHADER, vertexSrc);
    if (!vertResult.success) {
        return { valid: false, stage: 'vertex', error: vertResult.log };
    }

    const fragResult = compile(gl.FRAGMENT_SHADER, fragmentSrc);
    if (!fragResult.success) {
        gl.deleteShader(vertResult.shader);
        return { valid: false, stage: 'fragment', error: fragResult.log };
    }

    // Check program link status
    const program = gl.createProgram();
    gl.attachShader(program, vertResult.shader);
    gl.attachShader(program, fragResult.shader);
    gl.linkProgram(program);

    const linked = gl.getProgramParameter(program, gl.LINK_STATUS);
    let result = { valid: true, stage: null, error: null };

    if (!linked) {
        result = {
            valid: false,
            stage: 'linking',
            error: gl.getProgramInfoLog(program)
        };
    }

    // Clean up temporary resources
    gl.deleteProgram(program);
    gl.deleteShader(vertResult.shader);
    gl.deleteShader(fragResult.shader);

    return result;
}

Usage Example

Call the validator using your initialized Pixi application before binding the shader:

const check = validateShader(app.renderer, customVertexSrc, customFragSrc);

if (!check.valid) {
    console.warn(`Shader failed at ${check.stage}:`, check.error);
    // Fall back to a default material or display error in UI
} else {
    const shader = PIXI.Shader.from(customVertexSrc, customFragSrc);
    const mesh = new PIXI.Mesh(geometry, shader);
    app.stage.addChild(mesh);
}

Intercepting Pixi.js Internal Console Output

If you prefer to let Pixi.js manage compilation while still extracting the engine's formatted error message (which includes line-numbered source dumps), you can temporarily wrap console.error during the shader compilation phase:

function capturePixiShaderErrors(compileCallback) {
    const capturedErrors = [];
    const originalConsoleError = console.error;

    console.error = (...args) => {
        capturedErrors.push(args.join(' '));
        originalConsoleError.apply(console, args);
    };

    try {
        compileCallback();
    } finally {
        console.error = originalConsoleError;
    }

    return capturedErrors;
}

// Force Pixi to compile immediately and capture failures
const errors = capturePixiShaderErrors(() => {
    const shader = PIXI.Shader.from(brokenVertexSrc, brokenFragmentSrc);
    // Force compilation by triggering program extraction
    app.renderer.shader.bind(shader);
});

if (errors.length > 0) {
    // Process or report captured error logs
    handleCapturedLogs(errors);
}

Key Considerations

  • Deferred Compilation: In Pixi.js, shaders do not build when instantiated; they build when bound to the WebGL context via renderer.shader.bind(shader) or during the first render call.
  • Driver Differences: The formatting of gl.getShaderInfoLog() depends on the client's GPU driver and browser environment (e.g., ANGLE on Windows vs. native OpenGL on macOS/Linux).
  • WebGL vs. WebGPU (PixiJS v8): If using PixiJS v8 with the WebGPU renderer, shader errors occur at the WGSL pipeline compilation stage instead of WebGL. Use app.renderer.type === PIXI.RendererType.WEBGL to verify the active backend before relying on WebGL-specific error extraction.
