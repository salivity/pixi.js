PixiJS System Lifecycle Hooks Explained

Pixi.js utilizes a modular architecture where the main Renderer delegates tasks such as texture management, batching, and projection to specialized components known as Systems. When a System is registered and initialized within the Renderer, Pixi.js orchestrates its setup and runtime behavior through predefined lifecycle hooks and internal dispatchers called Runners. This article breaks down the specific lifecycle hooks available to a System during its initialization and lifecycle within the Pixi.js Renderer pipeline.

The System Lifecycle Architecture

In modern Pixi.js (notably v7 and v8), systems are designed as plugins attached to the Renderer. Instead of relying solely on standard class inheritance, Pixi.js uses the Runner pattern to dispatch events across all registered systems automatically. When a system is loaded, specific hooks are called sequentially to configure resources, respond to context changes, and prepare for rendering loops.

1. init(options)

The init method is the foundational lifecycle hook called during the renderer's initialization sequence.

  • When it executes: Invoked when renderer.init() is executed (or internally right after system registration if the renderer is already initialized).
  • Purpose: It receives the configuration options passed into the renderer. In modern Pixi.js versions, init can be asynchronous, allowing systems to load WebGPU pipelines, compile shaders, or allocate WebGL buffers before the first frame is rendered.
  • Usage: Use this method instead of the constructor for setup logic that depends on other systems, as all systems are guaranteed to be instantiated on the renderer instance by the time init runs.

2. contextChange(gl)

The contextChange hook handles the creation, loss, or restoration of the rendering context.

  • When it executes: Fired immediately after the graphics context (WebGL or WebGPU) is acquired by the context system during renderer initialization, as well as whenever a context loss or restore event occurs.
  • Purpose: Allows the system to allocate context-bound resources, such as WebGL state management, VAOs (Vertex Array Objects), texture bindings, and shader programs.
  • Signature: Typically receives the rendering context (gl or WebGPU device) as an argument.

3. resize(width, height, resolution)

The resize hook notifies systems whenever the canvas drawing buffer or viewport dimensions update.

  • When it executes: Called during initial setup once dimensions are first calculated, and subsequently whenever renderer.resize() is triggered.
  • Purpose: Used by systems that manage screen projections, view matrices, framebuffers, and render targets to recalculate viewport bounds and projection matrices matching the new canvas size.

4. prerender() and postrender()

While executed during the draw cycle rather than initialization, these hooks are registered during system initialization to participate in the rendering pipeline.

  • prerender(): Executes immediately before the scene graph traversal begins. Ideal for resetting batch states, clearing temporary buffers, and binding default render targets.
  • postrender(): Executes immediately after the scene graph has been fully drawn to the target, allowing systems to flush remaining draw calls, read back pixels, or perform frame cleanup.

5. destroy()

The final lifecycle hook handles disposal and memory cleanup.

  • When it executes: Invoked when renderer.destroy() is called.
  • Purpose: Cleans up references, unbinds event listeners, releases GPU allocations, and frees memory to avoid leaks. Systems should nullify references to the parent Renderer instance inside this method.
