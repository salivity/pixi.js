Serialize PixiJS Display Tree to JSON for Saves

Serializing a PixiJS display hierarchy into JSON requires traversing the scene tree, extracting essential transform and visual properties, and mapping them to lightweight data structures while ignoring internal engine objects like WebGL contexts and circular references. This guide explains how to build a recursive serialization system to export your PixiJS display tree to JSON and reconstruct it faithfully for game save states.

The Challenge of Direct Serialization

Passing a root PixiJS Container directly to JSON.stringify will fail due to circular references (parent pointing back to ancestors) and complex internal references (WebGL textures, event emitters, and renderers). To save game states cleanly, you must define a custom schema that extracts only the necessary visual and structural properties, then reconstruct the instances upon loading.

Defining the Serializable Schema

A reliable JSON representation of a display node requires identifying:

  1. Type: The class to instantiate (e.g., Container, Sprite, Text, Graphics).
  2. Transform Data: Coordinates, scale, rotation, pivot, skew, and alpha.
  3. Asset References: Texture keys or frame IDs from your asset manager, rather than raw texture objects.
  4. Custom Game State: Custom identifiers, interaction flags, or gameplay metadata attached to the display object.
  5. Children: An array of nested serializable node objects.

Implementing the Recursive Serializer

Traverse the display tree recursively starting from a root container. Read the relevant properties from each DisplayObject and compile them into a plain JavaScript object.

function serializeDisplayObject(object) {
  // Base node configuration
  const node = {
    type: object.constructor.name,
    x: object.x,
    y: object.y,
    scaleX: object.scale.x,
    scaleY: object.scale.y,
    rotation: object.rotation,
    alpha: object.alpha,
    visible: object.visible,
    zIndex: object.zIndex,
    name: object.name || null,
    customData: object.customData || {},
    children: []
  };

  // Extract type-specific properties
  if (object instanceof PIXI.Sprite) {
    // Store the asset key mapped to the texture, not the texture itself
    node.textureKey = object.textureKey || null;
    node.anchorX = object.anchor.x;
    node.anchorY = object.anchor.y;
    node.tint = object.tint;
  } else if (object instanceof PIXI.Text) {
    node.text = object.text;
    node.style = object.style.toObject ? object.style.toObject() : object.style;
  }

  // Recurse into children if the object is a container
  if (object.children && object.children.length > 0) {
    for (const child of object.children) {
      // Avoid saving transient objects such as debug overlays or UI cursors
      if (!child.doNotSerialize) {
        node.children.push(serializeDisplayObject(child));
      }
    }
  }

  return node;
}

// Convert root game stage or a container to JSON
function exportHierarchyToJSON(rootContainer) {
  const serializedTree = serializeDisplayObject(rootContainer);
  return JSON.stringify(serializedTree);
}

Handling Texture References

A common pitfall is attempting to serialize PIXI.Texture. Instead, store a string identifier representing the texture. Assign a textureKey property to your sprites during creation or asset loading:

const sprite = PIXI.Sprite.from('hero_idle.png');
sprite.textureKey = 'hero_idle.png';

When serializing, write this key to the JSON payload so the deserializer can fetch the appropriate texture from cache.

Implementing the Deserializer

Rebuilding the tree requires reading the JSON, using a factory pattern to instantiate the appropriate PixiJS classes, applying stored properties, and attaching children back to their parents.

function deserializeDisplayObject(node) {
  let instance;

  switch (node.type) {
    case 'Sprite':
      const texture = node.textureKey 
        ? PIXI.Texture.from(node.textureKey) 
        : PIXI.Texture.EMPTY;
      instance = new PIXI.Sprite(texture);
      instance.textureKey = node.textureKey;
      instance.anchor.set(node.anchorX, node.anchorY);
      if (node.tint !== undefined) instance.tint = node.tint;
      break;

    case 'Text':
      instance = new PIXI.Text(node.text, node.style);
      break;

    case 'Container':
    default:
      instance = new PIXI.Container();
      break;
  }

  // Restore transforms and visual attributes
  instance.x = node.x;
  instance.y = node.y;
  instance.scale.set(node.scaleX, node.scaleY);
  instance.rotation = node.rotation;
  instance.alpha = node.alpha;
  instance.visible = node.visible;
  instance.zIndex = node.zIndex;
  instance.name = node.name;
  instance.customData = node.customData;

  // Recursively reconstruct children
  if (node.children && node.children.length > 0) {
    for (const childNode of node.children) {
      const childInstance = deserializeDisplayObject(childNode);
      instance.addChild(childInstance);
    }
  }

  return instance;
}

// Recreate a container from a JSON string
function loadHierarchyFromJSON(jsonString) {
  const rootNode = JSON.parse(jsonString);
  return deserializeDisplayObject(rootNode);
}

Considerations for Complex Scenes

  • PixiJS Graphics: Serializing PIXI.Graphics by reading geometric paths can be inefficient. Instead, store high-level drawing parameters (e.g., shape: "circle", radius: 20) in customData and regenerate the vector paths during deserialization.
  • Filters and Shaders: Avoid saving WebGL filter objects directly. Store configuration arrays (e.g., [{ type: "ColorMatrixFilter", brightness: 0.5 }]) and reapply filters programmatically.
  • Decoupling Data from View: In large projects, avoid saving view-only objects directly. Store your game's underlying data model instead, and write a synchronization layer that updates the PixiJS display tree to match the restored game state.
