WebGPU Storage Buffers for Particles in PixiJS

This article examines how PixiJS v8 manages WebGPU storage buffer bindings to process arbitrary particle arrays inside custom compute passes. It details the lifecycle of storage buffers within the PixiJS WebGPU rendering abstraction, covering buffer allocation with correct usage flags, bind group compilation and resource layout reflection, memory synchronization, and execution via compute pipelines.

WebGPU Buffer Abstraction in PixiJS

PixiJS abstracts raw GPUBuffer allocations through its internal Buffer class. When dealing with arbitrary particle data destined for a compute shader, the buffer must be initialized with explicit usage flags to be valid as a storage target.

In WebGPU, a buffer cannot be bound as a storage resource unless it contains the GPUBufferUsage.STORAGE flag. In PixiJS, this is defined by combining flags via the BufferUsage bitmask:

  • BufferUsage.STORAGE: Allows the buffer to be bound as a var<storage, read> or var<storage, read_write> resource in WGSL.
  • BufferUsage.COPY_DST: Permits updating the buffer using queue.writeBuffer.
  • BufferUsage.VERTEX: Often combined with compute buffers so the compute output can be fed directly to a render pipeline as an instanced vertex attribute array without CPU readback.

When a PixiJS Buffer is initialized with a typed array (such as a Float32Array representing particle positions, velocities, and lifespans), the WebGPUBufferSystem lazily allocates the underlying hardware buffer during the preparation phase before dispatch.

Reflection and Bind Group Creation

PixiJS bridges shader declarations and JavaScript structures using its GpuProgram and BindGroup subsystems:

  1. Shader Reflection: When a WGSL compute shader is loaded, PixiJS parses or reflects the source code to locate resource declarations. It identifies storage variables defined with @group(X) @binding(Y) var<storage, ...> attributes and builds the internal bind group layout metadata.
  2. BindGroup Assignment: An instance of BindGroup is instantiated containing the storage Buffer assigned to the numeric binding slot defined in the WGSL compute code.
  3. Pipeline Layout Generation: When preparing to execute, PixiJS compares the shader's expected binding layout against the assigned BindGroup. It manages the WebGPU GPUBindGroupLayout and caches the resulting GPUBindGroup to avoid redundant WebGPU driver allocations across frames.

CPU-to-GPU Synchronization

For particle data initialized or updated on the CPU:

  • Modifying the data requires flagging the PixiJS Buffer as dirty via buffer.update().
  • Prior to opening the compute pass, the WebGPUBufferSystem resolves pending buffer updates. It issues a device.queue.writeBuffer() call to stream the altered byte slice directly into GPU memory.
  • If particles are simulated entirely on the GPU, CPU synchronization is skipped after the initial upload. The buffer remains resident in VRAM across frames, with the compute pass continuously mutating the buffer via read_write storage access.

Executing the Compute Pass

PixiJS does not expose a high-level scene graph object for compute operations; instead, compute operations are handled via low-level pipeline execution or custom render systems:

  1. Pipeline Retrieval: A ComputePipeline is acquired from the internal cache using the compute GpuProgram.
  2. Command Recording: The renderer accesses the current GPUCommandEncoder and invokes beginComputePass().
  3. Binding Resources: PixiJS binds the pipeline with setPipeline() and binds the associated storage BindGroup via setBindGroup(index, bindGroup).
  4. Dispatch: The developer issues dispatchWorkgroups(workgroupCountX, workgroupCountY, workgroupCountZ) based on the total particle count divided by the WGSL @workgroup_size declaration.
  5. Compute Pass Termination: The pass is closed via end().

Interoperability with Render Passes

Because WebGPU enforces validation rules regarding simultaneous read/write states, PixiJS relies on sequential pass encoding to prevent hazard conflicts.

Once the compute pass completes and is ended on the command encoder, the particle storage buffer is safe to use in a subsequent render pass. By supplying the identical buffer to a mesh or particle container configured with matching vertex attributes, the GPU reads the simulated data directly from the buffer without moving data across the PCIe bus.
