Pixi.js Filter Chaining Across Render Targets

Pixi.js processes sequential filters through an automated rendering pipeline managed by its internal filter system. Rather than attempting to combine distinct shader programs into a single execution pass, Pixi.js isolates each filter, passing intermediate image data down the chain using a technique known as framebuffer ping-ponging. This architecture allows complex, multi-stage visual effects to be applied incrementally to display objects while optimizing texture allocation and memory usage.

The Filter Pipeline Mechanism

When a display object has an array of filters assigned to its filters property, Pixi.js delegates the drawing routine to the renderer's FilterSystem. The system calculates the aggregate bounding box of the display object, factoring in any extra padding specified by each filter to avoid clipping soft edges, such as glows or blurs.

Once the bounds are established, the original display object is rendered into a temporary offscreen RenderTexture rather than directly to the canvas screen. This initial texture serves as the source input for the first filter in the array.

Ping-Ponging Intermediate Render Targets

To chain filters without allocating an unbounded number of textures, Pixi.js uses two alternating render targets—a method commonly referred to as "ping-ponging":

  1. Initial Draw: The object is drawn to the first intermediate render target (Texture A).
  2. First Filter Pass: The shader of the first filter reads Texture A as its uniform sampler and outputs the filtered pixels into a second target (Texture B).
  3. Subsequent Passes: The second filter takes Texture B as its input and renders into Texture A. This alternating cycle repeats for each subsequent filter in the chain.

By alternating between these two buffers, Pixi.js can execute an arbitrary number of shader passes using only a minimal set of textures in video memory.

Texture Pooling and Memory Management

Creating and destroying framebuffers on the GPU every frame causes significant performance overhead and garbage collection spikes. Pixi.js mitigates this through an internal texture pool (TexturePool).

During a filter pass:

  • The FilterSystem requests temporary render textures matching the size of the filtered area from the pool.
  • If a matching render target exists in the pool, it is reused immediately.
  • Once the filter chain finishes executing, intermediate targets are marked as free and returned to the pool for future frames.

The Final Output Pass

Pixi.js avoids an unnecessary copy operation on the final step of the chain. When the FilterSystem reaches the last filter in the array, it sets the render target destination to the target currently active before the filter pipeline started—typically the main screen buffer or a parent container's custom render target.

The final shader reads the output of the second-to-last filter and writes the completed visual result directly to the destination target, finalizing the chain with minimal GPU latency.
