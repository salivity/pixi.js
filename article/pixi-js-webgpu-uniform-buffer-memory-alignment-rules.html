Pixi.js WebGPU Uniform Buffer Memory Alignment Rules

Understanding memory alignment for uniform buffers in Pixi.js is essential when developing shaders for the WebGPU backend. Because WebGPU relies on strict memory layouts defined by the WGSL specification, data passed via uniform buffers must align to specific byte boundaries. This guide breaks down the core alignment and sizing rules for scalars, vectors, matrices, arrays, and structs to ensure data transfers correctly from CPU to GPU without corruption.

Base Alignment and Size Rules for Primitive Types

Every data type in WGSL has an inherent size and alignment rule (measured in bytes). In a WebGPU uniform buffer, an element's offset in memory must be an exact multiple of its alignment requirement:

  • f32, i32, u32:
    • Size: 4 bytes
    • Alignment: 4 bytes
  • vec2<f32>, vec2<i32>, vec2<u32>:
    • Size: 8 bytes
    • Alignment: 8 bytes
  • vec3<f32>, vec3<i32>, vec3<u32>:
    • Size: 12 bytes
    • Alignment: 16 bytes (Warning: While it holds 12 bytes of data, its starting position must align to 16 bytes, leaving a 4-byte trailing padding if followed by a scalar).
  • vec4<f32>, vec4<i32>, vec4<u32>:
    • Size: 16 bytes
    • Alignment: 16 bytes

Matrix Alignment

Matrices in WGSL are treated as column-major arrays of vectors. Each column vector adopts the alignment rules of its corresponding vector type:

  • mat4x4<f32>: Composed of four vec4<f32> columns.
    • Size: 64 bytes
    • Alignment: 16 bytes
  • mat3x3<f32>: Composed of three vec3<f32> columns.
    • Alignment: 16 bytes
    • Size: 48 bytes (Each column vector occupies 16 bytes of aligned memory, making the stride 16 bytes per column, totaling 48 bytes rather than 36 bytes).
  • mat2x2<f32>: Composed of two vec2<f32> columns.
    • Alignment: 8 bytes
    • Size: 16 bytes

Array Rules in Uniform Address Spaces

In uniform buffers, array elements must have an element stride rounded up to the nearest multiple of 16 bytes:

  • An array<f32, 4> in a uniform buffer does not take 16 contiguous bytes. Instead, each individual float is spaced by 16 bytes, consuming a total of 64 bytes.
  • To store packed data efficiently, group arrays into vec4 primitives rather than scalar arrays.

Struct Alignment and Padding

Structs in uniform buffers adhere to two primary rules:

  1. Member Placement: Each field starts at an offset that is a multiple of its own alignment. If the current byte offset is not properly aligned, padding bytes are inserted automatically.
  2. Total Struct Size: The total size of a struct must be a multiple of the largest alignment requirement among its members.

For example, a struct containing a vec3<f32> followed by an f32 will fit snugly into 16 bytes: the vec3 takes bytes 0–11, and the f32 (requiring 4-byte alignment) occupies bytes 12–15. However, if the f32 is declared first, it takes bytes 0–3, bytes 4–15 become padding, and the vec3 begins at byte 16, resulting in a 32-byte struct.

Buffer Binding Alignment

When binding sub-ranges of buffers with dynamic offsets in WebGPU, the offset must be an integer multiple of the device's minUniformBufferOffsetAlignment limit. This value is typically 256 bytes on most modern hardware.

Best Practices in Pixi.js

  • Order Uniforms by Decreasing Size: When structuring your UniformGroup in Pixi.js, arrange your variables from largest to smallest alignment (mat4, vec4, vec3, vec2, then scalars) to naturally prevent unintended padding.
  • Avoid vec3 When Possible: Use vec4 instead of vec3 to make the 16-byte alignment explicit and avoid confusion over hidden padding bytes.
  • Manual Buffers: If manually populating a Float32Array to back a uniform buffer, ensure your index calculations account for the 4-byte padding of vec3 and the 16-byte column strides of mat3x3.
