WebGPU vs WebGL Stencil Operations in Pixi.js

PixiJS abstracts hardware rendering across both WebGL and WebGPU, allowing developers to apply masks and stencil clipping without worrying about underlying graphic APIs. However, under the hood, Pixi.js handles stencil operations in vastly different ways depending on the backend. This article examines how Pixi.js translates imperative WebGL gl.stencilOp calls into declarative WebGPU pipeline states and render pass attachments.

State Machine vs. Immutable Pipeline States

The core difference between WebGL and WebGPU stencil management lies in their architecture. WebGL operates as a state machine. To write or update stencil values, PixiJS issues dynamic calls on the active context:

  • gl.stencilFunc(func, ref, mask) to define the test conditions and reference value.
  • gl.stencilOp(fail, zfail, zpass) to specify what happens to the stencil buffer when a fragment passes or fails.
  • gl.stencilMask(mask) to enable or disable writing to the stencil buffer.

In contrast, WebGPU decouples stencil configuration across two structures: immutable pipeline descriptors (GPURenderPipeline) and render pass descriptors (GPURenderPassDescriptor).

Because pipeline creation is expensive, PixiJS pre-configures and caches WebGPU pipelines containing depth-stencil states, rather than modifying global states right before a draw call.

Mapping gl.stencilOp to GPUStencilFaceState

WebGL’s gl.stencilOp takes three operations: one for stencil test failure (fail), depth test failure (zfail), and passing both tests (zpass).

In WebGPU, these correspond directly to properties within the stencilFront and stencilBack objects inside a pipeline’s depthStencil block:

  • fail maps to failOp
  • zfail maps to depthFailOp
  • zpass maps to passOp

PixiJS maps the standard WebGL stencil operation enums to WebGPU string tokens as follows:

  • gl.KEEP \(\rightarrow\) 'keep'
  • gl.ZERO \(\rightarrow\) 'zero'
  • gl.REPLACE \(\rightarrow\) 'replace'
  • gl.INVERT \(\rightarrow\) 'invert'
  • gl.INCR \(\rightarrow\) 'increment-clamp'
  • gl.DECR \(\rightarrow\) 'decrement-clamp'
  • gl.INCR_WRAP \(\rightarrow\) 'increment-wrap'
  • gl.DECR_WRAP \(\rightarrow\) 'decrement-wrap'

When masking in Pixi.js (such as writing an incrementing mask level for nested clipping), the engine constructs a WebGPU pipeline where passOp is set to 'increment-clamp' (or 'replace' depending on mask mode), mirroring what would have been passed as the third parameter to gl.stencilOp.

Render Pass Attachment Configuration

In WebGL, clearing or preserving the stencil buffer is handled imperatively via gl.clearStencil() and gl.clear(gl.STENCIL_BUFFER_BIT).

In WebGPU, stencil attachment behavior must be declared at the beginning of a render pass inside the GPURenderPassDepthStencilAttachment. Pixi.js configures the stencil lifecycle with:

  • stencilLoadOp: Set to 'clear' if a fresh stencil mask is being initialized, or 'load' if the existing stencil buffer contents must be preserved across draw batches.
  • stencilStoreOp: Set to 'store' to ensure written stencil values persist for subsequent render passes (or 'discard' if stencil results are transient).
  • stencilClearValue: Replaces gl.clearStencil(), usually defaulting to 0.

Dynamic Reference Values

While WebGPU requires immutable pipeline states for operation behaviors (failOp, passOp), it allows dynamic updates for the stencil reference value.

In WebGL, PixiJS updates reference values via gl.stencilFunc(func, ref, mask) during mask push/pop phases. In WebGPU, PixiJS avoids creating new pipelines for every mask depth by calling:

passEncoder.setStencilReference(stencilRefValue);

This dynamic command sets the reference value evaluated against the pipeline’s predefined compare function on the active render pass encoder, providing the exact same functionality as WebGL without pipeline recreation overhead.
