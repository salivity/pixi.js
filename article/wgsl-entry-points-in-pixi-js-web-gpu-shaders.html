WGSL Entry Points in Pixi.js WebGPU Shaders

In Pixi.js v8 and above, WebGPU Shading Language (WGSL) allows developers to write both vertex and fragment shader stages within a single source file or string. Entry points serve as the designated execution anchors that allow the WebGPU pipeline to distinguish between these two distinct stages during compilation. By explicitly declaring stage-specific entry functions within one shared codebase, Pixi.js simplifies shader management, enables shared data structures, and facilitates seamless GPU pipeline creation.

Stage Differentiation via Attributes

In WGSL, functions intended to run as shader stages are decorated with explicit stage attributes: @vertex and @fragment. When Pixi.js compiles a single shader string into a GPUShaderModule, the underlying WebGPU API parses the entire text at once.

The entry points indicate to the compiler which function represents the entry point for vertex operations (transforming geometries and computing clip-space coordinates) and which represents the fragment operations (calculating the color of each pixel). Without these designated entry points, the compiler cannot determine the operational boundaries of each stage from a unified script.

Mapping to the Render Pipeline

When Pixi.js builds a render pipeline using its WebGPU backend, it configures a GPURenderPipelineDescriptor. This descriptor requires references to both a vertex stage and a fragment stage:

  • Vertex Stage Configuration: Points to the compiled shader module and specifies the function labeled with @vertex (commonly named mainVertex or main depending on configuration).
  • Fragment Stage Configuration: Points to the exact same compiled shader module, but specifies the function marked with @fragment (commonly named mainFragment or main).

By isolating the execution targets through entry point identifiers, Pixi.js creates a complete, functional pipeline using a single module reference, avoiding the overhead of compiling multiple independent shader objects.

Shared Structs and Interface Consistency

Compiling vertex and fragment stages from a single source via distinct entry points guarantees data consistency between stages. In dual-source setups, data structures passed from the vertex shader to the fragment shader (varyings) must be maintained across two separate files, creating a potential source for mismatch errors.

In a single-source WGSL setup, an intermediate structure can be defined once:

struct VertexOutput {
    @builtin(position) position: vec4<f32>,
    @location(0) uv: vec2<f32>,
};

@vertex
fn mainVertex(...) -> VertexOutput {
    var output: VertexOutput;
    // ... vertex processing
    return output;
}

@fragment
fn mainFragment(input: VertexOutput) -> @location(0) vec4<f32> {
    // ... fragment processing using input.uv
}

Both the vertex entry point return type and the fragment entry point parameter type reference the identical VertexOutput declaration. This enforces strict type safety and interface matching at compile time.

Shared Uniforms and Helper Functions

Entry points also allow both stages to access shared global scope elements. Uniform buffer bindings, storage buffers, constants, and utility mathematical functions can be written once at the top of the WGSL file. The vertex entry point, the fragment entry point, and any internal subroutines they call can access these declarations directly, reducing code duplication and minimizing asset size.

Performance and Pipeline Caching

Pixi.js aggressively caches shader programs and pipeline states to maintain high rendering performance. When both stages share a single source, Pixi.js only needs to load, preprocess, and request compilation for one WGSL module per unique material. The WebGPU driver processes the syntax tree once and extracts the independent execution paths mapped to each entry point, leading to faster startup times and reduced memory overhead during pipeline creation.
