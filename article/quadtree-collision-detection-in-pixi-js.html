Quadtree Collision Detection in Pixi.js

Rendering thousands of interactive sprites at 60 frames per second is standard for Pixi.js, but computing collisions between them can instantly cripple performance due to exponential computational overhead. A quadtree data structure solves this bottleneck by recursively dividing the 2D canvas into four quadrants, grouping nearby objects together so that collision checks are only performed between adjacent entities. This article explains the architectural limitations of naive collision detection in JavaScript, the operational mechanics of a quadtree, and how spatial partitioning transforms massive Pixi.js scenes from unplayable lag to smooth, optimized execution.

The Problem: Naive \(O(n^2)\) Collision Checks

Pixi.js utilizes WebGL to rapidly render thousands of 2D sprites on the GPU, but physics calculations and collision detection run on the single-threaded CPU via JavaScript.

The most straightforward way to detect collisions is comparing every object against every other object in a nested loop. For \(n\) objects, this requires \(\frac{n(n - 1)}{2}\) calculations, creating an algorithmic time complexity of \(O(n^2)\).

  • With 100 objects, the CPU performs roughly 4,950 checks per frame.
  • With 2,000 objects, that number escalates to nearly 2,000,000 checks per frame.
  • At 60 FPS, the CPU has roughly 16.6 milliseconds to update logic and render. Two million comparisons will immediately cause the frame rate to collapse into single digits.

Most of these checks are entirely wasted because objects on opposite sides of the screen can never collide.

What is a Quadtree?

A quadtree is a specialized tree data structure designed for two-dimensional spatial partitioning. It works by decomposing a flat 2D plane into four equal sub-quadrants: North-West (NW), North-East (NE), South-West (SW), and South-East (SE).

A quadtree operates under a few simple rules:

  1. Capacity Limit: Each quadrant node has a designated capacity limit (for example, a maximum of 4 or 8 objects) and a maximum depth level to prevent infinite subdivision.
  2. Subdivision: When the number of objects within a node exceeds the capacity, the node splits itself into four child nodes.
  3. Distribution: Existing objects and new additions are distributed into the appropriate child nodes based on their coordinates and bounding boxes. Objects that intersect boundary lines are either kept at the parent level or referenced across multiple intersecting child nodes.

How a Quadtree Optimizes Pixi.js Performance

The quadtree acts as an ultra-fast "broad-phase" collision filter. Instead of running expensive hit-tests across the entire sprite array, the collision process is split into two phases:

  1. Broad-Phase (Quadtree Query): For a given Pixi.js sprite, you query the quadtree using the sprite's bounding box (sprite.getBounds()). The quadtree traverses only the relevant branch of the tree and returns a small array of candidate sprites located in the same or neighboring quadrants.
  2. Narrow-Phase (Precise Collision): You run detailed collision checks (such as Axis-Aligned Bounding Box (AABB) intersection or circle radius math) only against the small subset of candidates returned by the quadtree.

By discarding 95% or more of non-colliding entities before running math operations, the algorithmic complexity drops from \(O(n^2)\) down to roughly \(O(n \log n)\). A scene with 2,000 objects shifts from two million checks per frame to just a few thousand, keeping CPU execution well within the 16.6-millisecond frame budget.

Implementation Flow Within the Pixi.js Ticker

To use a quadtree with dynamic objects in Pixi.js, the tree must be updated in tandem with the rendering loop via PIXI.Ticker:

  1. Clear: At the beginning of the frame update, wipe the quadtree clean. Rebuilding the tree every frame is computationally cheaper than searching, removing, and re-inserting moving objects.
  2. Insert: Loop over all active Pixi.js sprites and insert their spatial bounds (x, y, width, height) into the quadtree.
  3. Query & Resolve: Iterate through your sprites once more. For each sprite, query the quadtree to retrieve nearby candidates, run your narrow-phase collision logic on that small group, and handle collision reactions accordingly.

By leveraging a quadtree for spatial awareness, you shift the CPU's workload from brute-force mathematical evaluation to structured memory traversal, allowing Pixi.js to handle thousands of colliding elements without dropping frames.
