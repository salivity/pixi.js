How PixiJS Determines MultiTexture Batch Limits

This article explores how Pixi.js optimizes 2D rendering performance through its multi-texture batching system by querying WebGL hardware capabilities, applying safety thresholds, and dynamically generating shaders to determine the maximum number of textures permitted per draw call.

Hardware Query via WebGL

The foundation of Pixi.js's multi-texture determination begins with the WebGL rendering context. Upon initialization, the batch system queries the graphics hardware to determine its architectural limits using standard WebGL calls:

gl.getParameter(gl.MAX_TEXTURE_IMAGE_UNITS);

This query returns the maximum number of simultaneous texture units accessible by the fragment shader on the current GPU. Hardware limits typically range from 8 on older mobile devices to 16 or 32 on modern desktop GPUs.

Safety Clamping and Internal Limits

Although a GPU may report a high capacity, such as 32 or more texture units, Pixi.js does not automatically use the maximum reported value. High numbers of samplers can lead to driver bugs, severe shader compilation latency, or exceed uniform vector limits on certain chipsets.

Pixi.js applies a default upper cap (historically configured via settings.SPRITE_MAX_TEXTURES or the batch renderer options). The system determines the usable texture count by taking the minimum value between the hardware capacity and the internal engine cap:

\[\text{maxTextures} = \min(\text{gl.MAX\_TEXTURE\_IMAGE\_UNITS}, \text{ENGINE\_MAX\_TEXTURES})\]

If a developer explicitly sets a custom texture limit in the renderer configuration, that value takes precedence as the upper bound, provided it does not exceed the hardware's MAX_TEXTURE_IMAGE_UNITS.

Dynamic Shader Generation

Once the batch system resolves the final integer for available textures, it generates a custom fragment shader tailored to that specific quantity.

  1. Sampler Arrays: The shader source is generated with a uniform array sized to the determined limit (e.g., uniform sampler2D uSamplers[%count%];).
  2. Conditional Unrolling: Because WebGL 1.0 does not consistently support non-constant indexing of sampler arrays, the batch shader generator programmatically builds an if-else or switch structure mapping the vertex texture ID attribute to the corresponding sampler uniform.

Runtime Batch Allocation

During rendering, the batch manager tracks unique texture references added to the current batch buffer:

  • As sprites are pushed into the batch, their textures are registered into a lookup array.
  • If a new sprite requires a texture that is not currently bound, and the lookup array has already reached the calculated limit, the batch renderer flushes the current geometry to the GPU.
  • The texture list is cleared, and a new batch is initiated with the incoming sprite.
