How Nested Stencil Masks Work in Pixi.js

Nesting multiple stencil masks in Pixi.js causes the renderer to compute the geometric intersection of all active masks, restricting visible pixels strictly to the overlapping region of every mask in the hierarchy. This article covers the internal mechanics of Pixi.js's stencil buffer management, how nesting depth affects the rendering pipeline, the technical limits imposed by WebGL, and the performance costs associated with nested masking.

Stencil Buffer Mechanics and Mask Stacking

When you assign a Graphics object as a mask to a display container in Pixi.js without configuring it as a sprite or texture mask, Pixi.js defaults to using the WebGL stencil buffer.

When masks are nested (for example, Container A has Mask A, and child Container B has Mask B), Pixi.js handles rendering via its internal MaskSystem and StencilSystem:

  1. Incrementing Stencil Levels: When Pixi.js enters a masked container, it flushes the current render batch and writes the mask's geometry into the stencil buffer. It increments the stencil buffer reference value for the affected pixels.
  2. Intersection (Logical AND): As execution descends into nested child masks, the inner mask is drawn only where the stencil buffer already matches the parent's level. The stencil value is incremented again. Consequently, rendering is confined solely to the intersection where all nested masks overlap.
  3. Restoring the Buffer: When exiting a container, Pixi.js runs a reverse pass to decrement the stencil buffer values back down, popping the mask from the internal stack and restoring the stencil state for remaining elements.

Nesting Depth Limits

WebGL context configurations typically allocate an 8-bit stencil buffer, which provides integer values ranging from 0 to 255.

While the hardware theoretically supports up to 255 increments, Pixi.js historically uses bitwise operations or specific integer levels depending on the major version (Pixi v5, v6, v7, and v8). In practice:

  • In standard configurations, you can safely nest masks up to several levels deep without visual artifacts.
  • Exceeding the internal limit of available stencil levels causes masks to fail silently, wrap around, or clip content unexpectedly.
  • If a project demands extreme nesting depth, the stencil buffer can run out of identifiable values, corrupting the visibility tests of sibling and parent elements.

Performance Impact

While stencil masks are more memory-efficient than alpha masks—because they do not require extra WebGL render textures—nesting them introduces notable performance overhead:

  • Batch Breaking: Every mask push and mask pop forces Pixi.js to flush its internal batch renderer. Nesting multiple masks creates numerous draw calls, preventing sprites from being batched together efficiently.
  • State Switching: Frequent modifications to the WebGL stencil state (gl.stencilFunc, gl.stencilOp, and color mask toggles) prevent the GPU pipeline from running at peak throughput.
  • Fill-Rate and Overdraw: Complex, overlapping vector shapes used as masks require the GPU to rasterize invisible geometry purely to set stencil flags, increasing fill-rate pressure on lower-end mobile devices.

Best Practices for Nested Stencil Masks

To maintain performance when using nested stencil masks:

  • Combine Geometry: Whenever possible, combine multiple static mask shapes into a single PIXI.Graphics object rather than nesting separate masked containers.
  • Clean Up Masks: Detach or disable masks (container.mask = null) as soon as they are off-screen or no longer needed to prevent unnecessary state switches during render loops.
  • Consider Scissor Masks: For simple rectangular clipping, use PIXI.Container.prototype.filterArea or a rectangular scissor test where supported, as it bypasses the stencil buffer entirely and incurs lower overhead.
