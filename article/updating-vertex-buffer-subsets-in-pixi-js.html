Updating Vertex Buffer Subsets in Pixi.js

Updating only a subset of a vertex buffer in Pixi.js allows you to stream vertex modifications—such as particle positions, procedural mesh morphs, or dynamic skeletal tweaks—to the GPU without the performance penalty of re-uploading an entire dataset. This guide explains how Pixi.js handles buffer updates, how to modify targeted vertex memory using typed array views, and how to issue direct partial updates via WebGL’s gl.bufferSubData for maximum throughput.

The Default Update Mechanism vs. Partial Updates

In standard Pixi.js workflows using PIXI.Geometry and PIXI.Buffer, calling buffer.update() flags the entire buffer as dirty. During the next render pass, Pixi.js uploads the full CPU-side Float32Array to the GPU using:

gl.bufferSubData(gl.ARRAY_BUFFER, 0, buffer.data);

While this avoids reallocating GPU memory with gl.bufferData, it still transfers every byte across the bus. When dealing with thousands of vertices where only a small range changes, transmitting the entire array causes unnecessary memory bus saturation. A true sub-update limits the upload strictly to the altered byte range.

Step 1: Modifying Local Buffer Data In-Place

Instead of recreating typed arrays, manipulate the existing Float32Array stored in your PIXI.Buffer using in-place operations or subarray slices.

// Assume a buffer with vertex positions (x, y) for 1,000 vertices
const vertexCount = 1000;
const positionData = new Float32Array(vertexCount * 2);
const positionBuffer = new PIXI.Buffer(positionData, false, false);

// Target specific vertices to update (e.g., vertices from index 100 to 110)
const startIndex = 100;
const updateCount = 10;
const componentCount = 2; // x, y

// Subarray slice representing the subset
const subData = positionData.subarray(
    startIndex * componentCount,
    (startIndex + updateCount) * componentCount
);

// Mutate your data in the subarray
for (let i = 0; i < subData.length; i += 2) {
    subData[i] += 1.0;     // x
    subData[i + 1] += 0.5; // y
}

Step 2: Executing a Direct Sub-Update to the GPU

To update only that slice on the GPU without triggering a full re-upload, bypass buffer.update() and interact with Pixi’s internal BufferSystem and the underlying WebGL context.

function uploadBufferSubset(renderer, pixiBuffer, subData, startVertexIndex, componentsPerVertex) {
    const gl = renderer.gl;

    // Ensure the buffer is bound in the current WebGL state
    renderer.buffer.bind(pixiBuffer);

    // Calculate byte offset: index * components * 4 bytes per Float32
    const byteOffset = startVertexIndex * componentsPerVertex * Float32Array.BYTES_PER_ELEMENT;

    // Direct subset upload to the bound WebGLBuffer
    gl.bufferSubData(gl.ARRAY_BUFFER, byteOffset, subData);
}

Do not increment pixiBuffer._updateID after this operation. Leaving the update ID unchanged ensures Pixi's default buffer pipeline does not overwrite your partial upload with a full array transfer later in the frame.

Integrating with the Render Loop

Perform the sub-update inside an event hook or render listener where the active renderer instance is available:

app.ticker.add(() => {
    // 1. Update your target values in the typed array view
    for (let i = 0; i < subData.length; i += 2) {
        subData[i] = Math.sin(Date.now() * 0.005) * 50;
    }

    // 2. Dispatch partial upload directly to GPU memory
    uploadBufferSubset(app.renderer, positionBuffer, subData, startIndex, componentCount);
});

Best Practices

  • Calculate Exact Byte Offsets: Ensure calculations account for BYTES_PER_ELEMENT (4 bytes for Float32Array or Uint32Array, 2 bytes for Uint16Array). Misaligned offsets will distort geometry attributes.
  • Avoid Allocation in Tick Loops: Instantiate your subarray views once during initialization. Calling .subarray() repeatedly inside render loops introduces unnecessary garbage collection overhead.
  • Batch Consecutive Changes: Group modified vertices contiguously in the buffer where possible. Issuing a single gl.bufferSubData call over one contiguous range is substantially faster than issuing multiple disjoint updates across scattered indices.
