Why PixiJS Audio Desyncs in Background Tabs

Audio desynchronization in backgrounded Pixi.js applications occurs because web browsers drastically throttle visual rendering loops while allowing underlying audio subsystems to continue running. When a user switches to another tab or minimizes the browser, the application's visual updates pause or drop to minimal frame rates to conserve CPU and battery power. Meanwhile, the audio continues to play on a separate hardware-clocked thread, creating an immediate rift between the application's visual state and its soundtrack.

The Core Cause: requestAnimationFrame Throttling

Pixi.js drives its internal update cycle using PIXI.Ticker, which relies by default on the browser's native requestAnimationFrame (rAF) API.

Browsers treat background tabs aggressively:

  • Frame Rate Throttling: When a tab loses focus, modern browsers (Chrome, Firefox, Safari) reduce rAF calls to 1 frame per second or suspend them entirely.
  • Logic Freezing: Because game logic, sprite updates, and state machines are typically hooked into app.ticker.add(), your entire simulation effectively pauses or crawls while hidden.

The Independent Audio Thread

Web audio playback does not rely on requestAnimationFrame. Instead, it operates through one of two mechanisms:

  1. Web Audio API (AudioContext): The Web Audio API operates on a separate high-priority, low-latency operating system audio thread. Its internal timeline (AudioContext.currentTime) is tied to the hardware sample rate, not the DOM render cycle. It never stops ticking simply because a tab is hidden.
  2. HTML5 <audio> Elements: Standard media elements are handled by the browser's media pipeline, which continues background decoding and playback unless explicitly instructed otherwise.

Because the visual engine is frozen by rAF throttling while the audio engine keeps running uninterrupted, the two systems diverge. If a character animation and a sound effect were triggered at the same time, the sound will finish playing long before the animation finishes its visual frames.

Delta Time Spikes Upon Tab Return

A secondary desync issue appears the moment the user returns to the tab. When the tab regains focus:

  • The Pixi.js ticker fires its next rAF callback.
  • The elapsed time (deltaTime) calculated since the last frame can be enormous—potentially seconds or minutes long.
  • Depending on how ticker logic is written, the engine may attempt to "catch up" by executing a massive delta step all at once, or it may drop frames entirely.

If visual events try to skip ahead while a long-running audio track is already mid-stream, visual triggers and audio cue points will permanently misalign.

Timer Clamping and Logic Loops

Developers sometimes attempt to decouple their game loop from Pixi's ticker by using JavaScript timers like setInterval or setTimeout. This does not resolve the issue. Browsers clamp background timers to run no more than once per second (1000ms), and in some power-saving modes, timer execution is throttled even further. The audio playback will still drastically outpace any background timer-driven logic.

How to Prevent Audio Desync

To maintain synchronization between Pixi.js and audio, implement one or more of the following patterns:

  • Use the Page Visibility API: Listen for the visibilitychange event on the document. When document.hidden is true, explicitly pause all audio sources and pause the Pixi ticker via app.ticker.stop(). Resume both when the document becomes visible again.
  • Sync Logic to Audio Time: Instead of relying on Pixi's ticker to calculate animation progress, drive critical time-sensitive visuals using the currentTime property of your AudioContext.
  • Cap Delta Time: Ensure app.ticker.maxFPS or custom delta caps are set to prevent massive time jumps when returning to a focused tab.
  • Web Workers for Unthrottled Loops: If gameplay logic must run continuously while backgrounded, offload the master clock to a Web Worker, as workers are not subject to the strict rAF pause applied to the main rendering thread.
