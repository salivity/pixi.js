Handling Dynamic Canvas Resizing in Pixi.js

Using an HTML canvas as an active TextureSource in Pixi.js allows developers to project procedural graphics, video frames, or secondary 2D contexts directly into a WebGL scene. When the underlying source canvas dynamically changes its dimensions, Pixi.js must manage texture reallocation, UV coordinate remapping, and WebGL buffer updates. This article covers the internal mechanics of how Pixi.js handles dynamic canvas resizing, how to properly notify the engine of dimension changes, and the performance implications on GPU memory.

The TextureSource Abstraction

In modern Pixi.js architecture, textures are decoupled into display containers (Texture) and the underlying image data provider (TextureSource, specifically CanvasSource for HTML canvas elements). The CanvasSource wraps the native <canvas> element and tracks its properties, such as pixel width, pixel height, and resolution.

When a native canvas element's dimensions are altered via JavaScript (canvas.width = newWidth; canvas.height = newHeight;), the browser automatically clears the 2D context and resets its internal drawing buffer. However, Pixi.js operates in its own rendering loop and does not passively observe DOM attribute mutations on native elements every frame due to performance constraints.

Propagating Dimension Changes

Because Pixi.js does not poll the canvas for size changes automatically, you must explicitly notify the TextureSource when the canvas size changes. This is achieved using the resize method on the source:

// Change native canvas dimensions
nativeCanvas.width = 1024;
nativeCanvas.height = 768;

// Redraw content to the native context if needed
const ctx = nativeCanvas.getContext('2d');
ctx.fillStyle = 'red';
ctx.fillRect(0, 0, 1024, 768);

// Inform Pixi.js of the change
pixiTexture.source.resize(1024, 768);
pixiTexture.source.update();

Calling source.resize() updates the internal width and height registered inside the CanvasSource and flags the source as dirty (_dirtyId++).

WebGL Texture Reallocation

WebGL does not support dynamic resizing of an existing allocated GPU texture buffer. When a texture changes size, Pixi.js cannot simply append new pixel data; it must recreate or rebind the texture on the GPU.

  1. Dirty Flag Detection: On the next render tick, Pixi's TextureSystem checks the dirty state of all bound sources.
  2. Buffer Destruction and Creation: If the dimensions recorded in CanvasSource do not match the dimensions of the currently bound WebGL texture buffer, Pixi.js invokes gl.texImage2D with the new dimensions. The previous GPU allocation is released, and a new texture storage block is initialized in VRAM.
  3. Data Upload: The current pixel content of the 2D canvas is uploaded to the newly allocated GPU texture.

If you modify the contents of the canvas without changing its dimensions, calling source.update() is sufficient. This marks the texture as dirty for upload without triggering GPU memory reallocation.

UV Mapping and Sprite Bounds

When the underlying TextureSource is resized, any Texture instances relying on that source must recalculate their UV coordinates. Pixi.js handles this through internal event listeners:

  • The CanvasSource emits a resize event.
  • Connected Texture instances catch this event and recalculate their frames if configured to use the full source dimensions.
  • Normalized texture coordinates (\(0.0\) to \(1.0\)) are updated to prevent visual distortion, stretching, or unexpected cropping on attached Sprite or Mesh objects.

If a sprite depends on fixed pixel dimensions rather than dynamic scaling, its local bounds will update to match the new source width and height, shifting neighboring elements if they rely on dynamic layout calculations.

Performance Considerations

Dynamically resizing an active canvas TextureSource is computationally expensive compared to regular pixel updates:

  • Garbage Collection and Memory Churn: Frequent allocation and destruction of WebGL textures generate memory pressure on the GPU and can induce stutter.
  • Canvas Reset Overhead: Changing canvas dimensions resets the 2D rendering context, requiring a full repaint of the native canvas source.

For scenarios requiring frequent dimension adjustments (such as responsive UI panels or window resize events), resize events should be debounced. Alternatively, allocate a fixed, larger canvas initially and adjust the Texture frame boundaries rather than modifying the root canvas DOM dimensions.
