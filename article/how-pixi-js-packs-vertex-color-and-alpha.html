How Pixi.js Packs Vertex Color and Alpha

Pixi.js optimizes 2D rendering performance by packing vertex color and alpha components into the memory footprint of a single 32-bit float. Instead of passing four separate 32-bit floating-point numbers for Red, Green, Blue, and Alpha (which would consume 16 bytes per vertex), Pixi.js compresses the RGBA channels into 8-bit unsigned integers. By sharing an underlying ArrayBuffer between Float32Array and Uint32Array views, the engine writes a single 32-bit unsigned integer into the vertex buffer, which WebGL then consumes as four normalized unsigned bytes.

The Problem with Standard Float Attributes

In standard WebGL pipelines, defining a color attribute as a vec4 of floats requires:

  • Red: 32 bits (4 bytes)
  • Green: 32 bits (4 bytes)
  • Blue: 32 bits (4 bytes)
  • Alpha: 32 bits (4 bytes)

This results in 16 bytes per vertex exclusively dedicated to color. Because Pixi.js frequently pushes hundreds of thousands of vertices per second in high-density 2D scenes, this data overhead wastes CPU-to-GPU bus bandwidth and reduces cache efficiency.

Bitwise Packing and Premultiplication

Pixi.js compresses these four components into a single 32-bit integer (4 bytes total). Color inputs in Pixi.js typically arrive as a hexadecimal number (0xRRGGBB) alongside an alpha value between 0.0 and 1.0.

Before writing to the buffer, Pixi.js performs color premultiplication and bit shifting:

  1. Extract Components: The 24-bit hexadecimal color is split into individual 8-bit integers (0–255) for Red, Green, and Blue.
  2. Premultiply Alpha: If premultiplied alpha is enabled, each RGB channel is multiplied by the alpha float value and rounded.
  3. Pack into 32 Bits: The values are bit-shifted into an unsigned 32-bit integer in ABGR format:
const r = (color >> 16) & 0xFF;
const g = (color >> 8) & 0xFF;
const b = color & 0xFF;
const a = (alpha * 255) & 0xFF;

const packedColor = (a << 24) | (b << 16) | (g << 8) | r;

ABGR ordering is chosen because most consumer architectures are little-endian. When read sequentially in memory byte-by-byte, the order becomes R, G, B, and A.

ArrayBuffer Aliasing (Type Punning)

An IEEE-754 32-bit float cannot reliably store arbitrary 32-bit bitmasks using direct mathematical assignment, as the 24-bit significand causes data loss in the remaining bits. Pixi.js solves this by avoiding float conversion entirely at the JavaScript level.

Pixi creates an ArrayBuffer representing the vertex data and attaches two distinct typed array views over the same memory address:

const buffer = new ArrayBuffer(vertexByteSize);
const float32View = new Float32Array(buffer);
const uint32View = new Uint32Array(buffer);

When building vertex data:

  • Positions (X, Y) and Texture Coordinates (U, V) are written using float32View.
  • The packed color is written into uint32View at the index corresponding to that vertex's color slot.

Because both views point to the exact same memory, the 32-bit integer occupies the exact space of one float without altering the underlying bits.

WebGL Attribute Configuration

On the GPU side, Pixi.js tells WebGL how to read that 4-byte slot via gl.vertexAttribPointer:

gl.vertexAttribPointer(
    colorAttributeLocation,
    4,                  // 4 components: R, G, B, A
    gl.UNSIGNED_BYTE,   // Read as 8-bit bytes, not 32-bit floats
    true,               // Normalize: maps [0, 255] to [0.0, 1.0]
    strideInBytes,
    offsetInBytes
);

By configuring the attribute type as gl.UNSIGNED_BYTE with normalized = true, the GPU reads the single 32-bit memory slot as four 8-bit values and automatically converts them to a vec4(r, g, b, a) containing float values between 0.0 and 1.0 inside the vertex shader. This eliminates 12 bytes per vertex while retaining standard shader compatibility.
