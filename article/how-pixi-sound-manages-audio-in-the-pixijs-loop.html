How Pixi Sound Manages Audio in the PixiJS Loop

The @pixi/sound library combines the high-performance Web Audio API with PixiJS's Ticker system to synchronize audio playback with visual rendering. While the browser's audio engine processes sound buffers on a separate background thread to ensure uninterrupted playback, @pixi/sound hooks directly into the PixiJS render loop to update dynamic properties like fades, spatial positioning, and time tracking on every frame. This design prevents visual stutter from interrupting sound while keeping audio-driven gameplay logic strictly aligned with screen refreshes.

Web Audio Thread vs. The Visual Render Loop

PixiJS renders graphics on the main JavaScript thread via requestAnimationFrame, executing logic and drawing frames at the display's refresh rate (typically 60Hz or higher). In contrast, the Web Audio API runs on an independent, hardware-level audio processing thread.

@pixi/sound delegates audio synthesis, decoding, and playback buffering directly to the browser's AudioContext. Because audio rendering is offloaded to this separate thread, heavy graphical processing, large asset uploads, or temporary frame drops on the main thread do not cause audio buffer underruns, stuttering, or crackling.

Integration with PIXI.Ticker

To manage state changes that depend on visual frames, @pixi/sound binds directly to PIXI.Ticker.shared. The library uses the ticker's delta time to process continuous updates without relying on separate setInterval or setTimeout mechanisms.

During each execution of the ticker:

  • Volume and Property Tweens: Fades, volume ramps, and speed adjustments are updated incrementally using the frame's elapsed delta time.
  • Filter and Effect Updates: Real-time adjustments to Web Audio node parameters—such as low-pass filters, distortion, or spatial panning—are synchronized with moving display objects.
  • Instance Tracking: Sound instances are monitored for completion. When a sound ends, the ticker-bound update routine triggers callbacks, releases memory, and recycles the instance pool.

Handling Page Visibility and Ticker Pauses

A key advantage of synchronizing with PixiJS is unified lifecycle management. When a user navigates away from the browser tab or minimizes the window, PixiJS automatically pauses its shared ticker to conserve CPU and GPU cycles.

@pixi/sound listens to these lifecycle events. When the ticker stops or visibility changes, the library suspends the underlying AudioContext or pauses active sound instances. Once the tab regains focus or the ticker resumes, audio playback unpauses seamlessly, ensuring audio and visual timelines stay completely in sync.

HTML5 Audio Fallback

When running in legacy environments where the Web Audio API is unavailable, @pixi/sound falls back to the HTML5 Audio element. Under this mode, precise frame-by-frame synchronization is reduced, as audio nodes cannot be directly manipulated. The library continues to use the PixiJS ticker to poll the currentTime of active audio elements, emulating event firing and volume transitions to preserve a consistent API across both rendering modes.
