How Pixi.js Reuses Pooled Framebuffers in Filters

Pixi.js utilizes an internal render texture and framebuffer pooling mechanism to eliminate the performance overhead associated with continuous GPU memory allocation during filter rendering. When applying graphical filters—such as blurs, color adjustments, or displacement maps—the rendering pipeline requires intermediate offscreen render targets to process pixel data. Rather than creating and destroying WebGL framebuffers and textures on every frame, Pixi.js recycles them through a managed pool, maintaining a consistent GPU memory footprint, mitigating CPU-to-GPU synchronization stalls, and preventing garbage collection spikes.

The Cost of Dynamic GPU Allocations

In WebGL, creating a framebuffer and its backing texture involves API calls such as gl.createFramebuffer(), gl.createTexture(), and gl.texImage2D(). Executing these calls during an active render loop causes severe performance degradation:

  • GPU Reallocation Latency: Allocating VRAM disrupts the GPU command stream, forcing pipeline flushes.
  • Garbage Collection Pressure: JavaScript objects representing discarded textures and framebuffers trigger garbage collection pauses on the CPU.
  • Texture Thrashing: Continuously allocating and deallocating differently sized textures leads to VRAM fragmentation.

The Role of RenderTexturePool

Pixi.js circumvents allocation overhead using an internal class named RenderTexturePool. Managed directly by the renderer's FilterSystem, this pool acts as a cache for offscreen render targets.

When a filter pass requires a destination target, it queries the pool instead of invoking WebGL allocation methods. The pool retains previously instantiated RenderTexture and Framebuffer objects in memory arrays. When a pass finishes, the texture is returned to the pool rather than being destroyed.

The Filter Lifecycle: Texture Acquisition and Release

The lifecycle of pooled framebuffers during filtering follows a strict push and pop sequence within the FilterSystem:

  1. Acquiring Textures (getFilterTexture): When preparing to render a filtered display object, the filter system calls getFilterTexture(). The pool checks its internal cache for an existing render target that matches the required dimensions, resolution, and multisample state. If a match exists, it is removed from the free list and assigned to the active filter pass.
  2. Ping-Pong Rendering: Multi-pass filters (such as a two-pass Gaussian blur requiring separate horizontal and vertical runs) request multiple intermediate textures. Pixi.js alternates rendering between two pooled framebuffers—reading from one and writing to the other—without generating new GPU resources.
  3. Releasing Textures (returnFilterTexture): Once all passes are complete and the final output is composited into the main render target or parent framebuffer, returnFilterTexture() returns the temporary render textures back to the pool. The textures are marked as available for immediate reuse in subsequent filter operations within the same frame.

Dimension Matching and Viewport Optimization

Reusing framebuffers requires handling objects of varying bounding box sizes. Pixi.js optimizes framebuffer reuse through dimension matching strategies:

  • Screen-Sized Pooling: For fullscreen filters, the pool reuses textures identical in size to the main canvas view. Because the resolution remains constant, these framebuffers are reused frame after frame with zero structural modification.
  • Power-of-Two and Bucket Sizing: To avoid allocating an exact-dimension texture for every uniquely sized sprite, the pool can round requested sizes up to predetermined increments or power-of-two boundaries. A smaller object simply renders into a sub-region of a larger pooled framebuffer using gl.viewport to restrict the draw area.
  • Viewport Clipping: Because only the relevant portion of the pooled texture is sampled, stale pixel data outside the active viewport is ignored. This eliminates the need to resize or clear unused regions of the underlying GPU texture.

Memory Management and Cleanup

Pooled framebuffers persist across frames to sustain high performance. To prevent excessive VRAM consumption when screen sizes change or peak filter demand subsides, Pixi.js incorporates cleanup routines:

  • Frame Counter Aging: Unused pooled textures track an internal frame age counter. If a texture remains unrequested for a defined number of frames, the system flags it as stale.
  • Explicit Garbage Collection: The pool periodically evicts aged framebuffers, calling gl.deleteFramebuffer() and gl.deleteTexture() to release VRAM back to the operating system safely outside critical draw paths.
  • Manual Cache Clearing: Developers can trigger renderer.texturePool.clear() to purge all cached resources when transitioning between distinct application states or scenes.
