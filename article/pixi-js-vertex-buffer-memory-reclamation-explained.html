Pixi.js Vertex Buffer Memory Reclamation Explained

This article provides an overview of how Pixi.js manages and reclaims vertex buffer memory when clearing scenes or removing display objects. It explores Pixi's dual approach to GPU memory: the pooling and reuse of pre-allocated buffers within its batch rendering pipeline, and the explicit destruction lifecycle required to delete dedicated WebGL buffers from GPU VRAM.

The Batching System and Static Buffer Reuse

For standard 2D elements such as sprites, simple graphics, and text, Pixi.js relies on an internal batching pipeline (BatchRenderer and BatchSystem). Instead of creating distinct GPU vertex buffers for every individual object, Pixi writes vertex data sequentially into pre-allocated, shared vertex buffers dynamically each frame.

When you clear a scene containing batched elements (for example, by calling stage.removeChildren()):

  • No WebGL buffers are destroyed.
  • The internal batch system simply resets its buffer write offsets back to zero for the upcoming frame.
  • The pre-allocated GPU memory remains reserved to avoid the heavy performance overhead associated with constantly creating (gl.createBuffer) and deleting (gl.deleteBuffer) WebGL buffers.

Dedicated Geometries and Meshes

Non-batched elements—such as Mesh, SimpleMesh, or custom Geometry instances—allocate their own discrete WebGL vertex and index buffers. These buffers reside directly in GPU memory.

Merely removing these objects from the scene graph (container.removeChild(mesh)) does not trigger vertex buffer reclamation. The display object is excluded from the render loop, but the underlying Geometry and its Buffer instances remain allocated on the GPU to allow for instant re-insertion without re-upload penalties.

Explicit Destruction via destroy()

To release vertex buffer memory back to the GPU, Pixi.js requires explicit destruction. Memory deallocation follows a strict cascading lifecycle:

  1. Triggering Disposal: Calling mesh.destroy({ children: true }) or geometry.destroy() flags the associated buffers for destruction.
  2. Buffer System Interception: Pixi’s BufferSystem tracks every active buffer through a unique ID mapped to internal WebGL context references.
  3. Hardware Deallocation: The BufferSystem.dispose(buffer) method executes the native WebGL call: 
    gl.deleteBuffer(webGLBuffer);
  4. Cache Invalidation: References to the buffer inside Pixi's internal binding cache and vertex array object (VAO) system are cleared to prevent dangling pointer references.

CPU Garbage Collection vs. GPU Memory Reclamation

A common pitfall occurs when scene nodes are dereferenced in JavaScript without calling .destroy(). While JavaScript’s garbage collector will eventually reclaim the CPU-side typed arrays (such as Float32Array), it cannot automatically notify the WebGL context to free the corresponding VRAM allocations. Without calling .destroy(true) on containers or their underlying geometries during a scene transition, vertex buffers will permanently leak in GPU memory until the WebGL context itself is destroyed.
