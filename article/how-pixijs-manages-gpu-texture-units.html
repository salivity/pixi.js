How PixiJS Manages GPU Texture Units

This article explores the internal architecture PixiJS uses to handle large volumes of distinct textures within GPU hardware limitations. It covers how PixiJS queries device capabilities, bundles draw operations through multi-texture batching, dynamically assigns sampler arrays in custom shaders, and flushes render batches when texture unit limits are reached.

The Hardware Limit: Maximum Texture Image Units

Web browsers and GPUs enforce a strict limit on how many textures can be bound concurrently during a single draw call. This limit is defined by the WebGL constant gl.MAX_TEXTURE_IMAGE_UNITS. On mobile devices, this is typically 8 or 16, while desktop environments frequently support 16 or 32.

If a scene contains dozens of unique base textures, PixiJS cannot bind all of them simultaneously. Instead, it must dynamically schedule and swap textures across these fixed hardware slots without causing severe performance degradation from excessive draw calls.

Multi-Texture Batching Architecture

PixiJS processes 2D render objects using a specialized batch rendering pipeline. Rather than drawing sprites individually—which would trigger a distinct draw call and texture bind for every single element—PixiJS collects sequential sprites into a single geometry buffer.

When managing textures within a batch, the BatchRenderer follows this workflow:

  1. Capacity Discovery: During renderer initialization, PixiJS queries gl.getParameter(gl.MAX_TEXTURE_IMAGE_UNITS) and establishes a safe upper bound (often capped via internal settings, such as maxTextures).
  2. Sequential Registration: As PixiJS iterates through the display list, it inspects each sprite's BaseTexture.
  3. Texture ID Assignment: If the texture is already registered in the current batch, PixiJS assigns its existing local index (ranging from 0 to maxTextures - 1). If it is a new texture, it is added to the active texture list and assigned the next available index.
  4. Vertex Attribute Injection: The assigned local index is written directly into the vertex data of that sprite as an attribute (commonly aTextureId).

Shader Generation for Multi-Texture Sampling

To handle multiple textures in a single draw call, PixiJS generates a fragment shader tailored to the device's maximum texture limit.

In WebGL, sampler arrays cannot always be indexed dynamically with non-constant expressions across all hardware. To guarantee cross-platform compatibility, PixiJS builds a custom shader containing a conditional lookup structure or a unrolled switch-case pattern:

uniform sampler2D uSamplers[%count%];
varying float vTextureId;
varying vec2 vTextureCoord;

void main(void) {
    vec4 color;
    if (vTextureId < 0.5) {
        color = texture2D(uSamplers[0], vTextureCoord);
    } else if (vTextureId < 1.5) {
        color = texture2D(uSamplers[1], vTextureCoord);
    }
    // ... continues up to the batch limit
    gl_FragColor = color * vColor;
}

By reading the vTextureId passed from the vertex shader, the GPU routes the pixel lookup to the correct sampler unit within a single draw execution.

The Flush Cycle: Handling Texture Capacity Overflow

When the rendering loop encounters a sprite whose BaseTexture would cause the batch to exceed the available GPU texture units, a "batch break" occurs:

  1. Flush Current Buffer: PixiJS halts the collection process and triggers a flush().
  2. Bind Active Textures: The accumulated unique textures are bound sequentially to gl.TEXTURE0, gl.TEXTURE1, up to gl.TEXTURE(N-1).
  3. Issue Draw Call: PixiJS submits the accumulated vertex buffer to the GPU using gl.drawElements().
  4. Reset State: The active texture registry and geometry buffers are cleared.
  5. Begin Next Batch: The sprite that triggered the overflow becomes the first entry in a fresh batch, assigned to local texture index 0.

Practical Implications for Rendering Performance

Because PixiJS batches textures based on display-list order, alternating between dozens of unbatched textures can force a flush on nearly every sprite, negating the benefits of batching.

To maintain high throughput when using dozens of distinct textures, developers should consider:

  • Sprite Sheets and Atlases: Packing many distinct images into a single larger image ensures they share a single BaseTexture, entirely bypassing texture unit switches.
  • Display Tree Sorting: Grouping sprites that share textures together in the display list minimizes the frequency of batch breaks, allowing PixiJS to fully utilize its multi-texture capacity on each draw call.
