Detect Memory Leaks in PixiJS Textures and Listeners

Unreleased GPU textures and dangling event listeners are the two most common causes of performance degradation and memory bloat in Pixi.js applications. This guide details how to identify, track, and isolate these memory leaks using Chrome DevTools, internal Pixi.js cache inspections, and proper disposal patterns. By understanding how the JavaScript garbage collector interacts with WebGL resources, you can quickly locate retained references and ensure your scenes clean up properly.

Understanding Pixi.js Leaks: CPU vs. GPU

Memory leaks in Pixi.js manifest in two distinct areas:

  1. CPU Memory (Heap): Lingering JavaScript references to objects, functions, and listeners that prevent the garbage collector (GC) from reclaiming memory.
  2. GPU Memory (VRAM): WebGL textures and buffers that remain allocated on the graphics card even if the CPU-side JavaScript objects representing them have been dereferenced.

Failing to remove an event listener keeps the host display object in CPU memory, which in turn retains its parent container and underlying textures. Conversely, removing a sprite from the display tree without destroying its underlying texture leaves that texture stranded in GPU memory.

Detecting Leaks with Chrome DevTools Heap Snapshots

Chrome DevTools provides the most reliable way to identify retained CPU objects.

  1. Open Chrome DevTools and navigate to the Memory panel.
  2. Select Heap snapshot and click Take snapshot to capture a baseline state.
  3. Perform the action that should allocate and then clean up memory (for example, opening and closing an in-game menu or switching levels).
  4. Click the trash can icon in the DevTools toolbar to force garbage collection.
  5. Take a second heap snapshot.
  6. Change the snapshot view dropdown from Summary to Comparison to compare Snapshot 2 against Snapshot 1.

What to Look For:

  • PIXI.Texture and PIXI.BaseTexture: If these counts have a positive # Delta after a scene transition, textures are not being freed.
  • EventEmitter or Listener: Pixi's display objects extend event emitters. A positive delta indicates handlers are still attached.
  • Detached HTMLCanvasElement: Indicates that offscreen render textures or canvas contexts are hanging around without disposal.

Inspect the Retainers tree at the bottom of the Memory panel for any leaked object. Expand the tree to identify the specific variable, array, or closure holding the reference.

Inspecting Texture Caches Directly

Pixi.js maintains internal registries to avoid re-uploading duplicate image data. Even if you discard all direct references to a texture, it remains in memory if it is still registered in the cache.

You can inspect the state of cached textures at runtime using the console:

// For Pixi.js v7+
console.log(PIXI.Assets.cache);

// For older Pixi.js versions
console.log(PIXI.utils.TextureCache);
console.log(PIXI.utils.BaseTextureCache);

If you navigate between scenes and see the number of keys in these cache objects continuously grow, your assets are not being purged. Ensure you release them via the assets API:

// Unload an asset and remove its texture from GPU memory
await PIXI.Assets.unload('path/to/asset.png');

Finding Unreleased Event Listeners

Event listeners typically leak when anonymous functions or bound methods are registered and never removed, preventing their scope from being collected.

Display Object Listeners

In Pixi.js, objects listening for interaction events (such as pointerdown) retain references to their callbacks:

// Leaking pattern:
button.on('pointerdown', this.onButtonClick, this);
// If button is removed without off(), 'this' remains in memory.

To verify whether listeners are cleared:

  1. Select the component in your code and check button._events.
  2. Inspect the returned object keys to see if callbacks are still actively bound.
  3. Use the DevTools Heap Snapshot, search for Listener, and check the retainers for references pointing back to your controller or state classes.

To resolve this, explicitly remove listeners or rely on Pixi's built-in cleanup mechanisms:

button.off('pointerdown', this.onButtonClick, this);
// Or remove all listeners at once:
button.removeAllListeners();

Using the DevTools Performance Panel

The Performance panel helps visualize overall trends over extended periods:

  1. Open the Performance panel and check the Memory checkbox.
  2. Click Record, interact with your application repeatedly (e.g., open/close a view 10 times), and click Stop.
  3. Observe the generated memory timeline.

In a healthy application, the JS Heap and Node counts resemble a sawtooth pattern: memory rises during use and drops sharply after a garbage collection event. If the baseline floor of the sawtooth consistently steps upward with each iteration, a leak is present.

Implementing Proper Disposal Patterns

Most Pixi.js leaks occur because developers remove an object from the stage via removeChild() without destroying it. removeChild() only detaches the item from the scene graph; it does not clear GPU data or event bindings.

Always invoke the destroy() method when a display object or texture is no longer needed:

// Destroy a container and all of its children, textures, and base textures
container.destroy({
    children: true,
    texture: true,
    baseTexture: true
});

Using these flags ensures that display nodes, CPU-side caches, WebGL texture buffers, and internal interaction listeners are completely stripped and marked for garbage collection.
