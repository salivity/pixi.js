How to Create a Custom Cache Parser in PixiJS

This guide covers how to implement a custom cache parser extension in PixiJS to manage proprietary and non-standard asset formats. You will learn the structure of the PixiJS CacheParser interface, how to register the extension into the global pipeline, and how to define keys to store primary assets and their nested sub-assets efficiently in memory.

Understanding the Cache Parser Architecture

PixiJS handles asset management through the @pixi/assets package, which separates loading, parsing, and caching into modular extensions. When an asset finishes loading, PixiJS checks registered CacheParser extensions to determine how the parsed object should be stored in memory.

A custom cache parser must implement the CacheParser interface, which consists of:

  • extension: Configuration metadata defining the extension type (ExtensionType.CacheParser).
  • test: A validation function that inspects the loaded asset and returns true if this parser should handle it.
  • getCacheableAssets: A mapping function that returns an object containing key-value pairs representing how the asset and any sub-assets should be indexed in the cache.

Implementing the Custom Parser

Suppose your application loads a proprietary format, such as a custom binary bundle containing map data and embedded textures, parsed into a CustomBundle object:

class CustomBundle {
    constructor(metadata, layers, textures) {
        this.__isCustomBundle = true;
        this.metadata = metadata;
        this.layers = layers;
        this.textures = textures; // Dictionary of Texture objects
    }
}

To register this asset properly in the PixiJS cache, create an extension object:

import { extensions, ExtensionType } from 'pixi.js';

export const customBundleCacheParser = {
    extension: {
        type: ExtensionType.CacheParser,
        name: 'customBundleCacheParser',
    },

    test(asset) {
        return asset && asset.__isCustomBundle === true;
    },

    getCacheableAssets(keys, asset) {
        const out = {};

        // Map primary asset keys (URLs, aliases) to the main bundle
        keys.forEach((key) => {
            out[key] = asset;

            // Cache individual sub-textures for direct access
            if (asset.textures) {
                Object.entries(asset.textures).forEach(([textureName, texture]) => {
                    out[`${key}/${textureName}`] = texture;
                });
            }
        });

        return out;
    }
};

Registering the Extension

Add the custom cache parser to PixiJS before calling any asset initialization or load routines:

import { Assets, extensions } from 'pixi.js';
import { customBundleCacheParser } from './customBundleCacheParser';

// Register the custom cache parser
extensions.add(customBundleCacheParser);

async function init() {
    await Assets.init();

    // Load your custom proprietary asset
    const bundle = await Assets.load('assets/world_01.custombundle');

    // Retrieve the entire bundle from the cache
    const cachedBundle = Assets.cache.get('assets/world_01.custombundle');

    // Retrieve an indexed sub-texture directly from the cache
    const subTexture = Assets.cache.get('assets/world_01.custombundle/tile_ground');
}

init();

Integration with Custom Loader Parsers

A cache parser does not load or parse raw files; it only indexes objects that have already been resolved. For proprietary files, you must pair your CacheParser with an ExtensionType.LoadParser. The load parser downloads the binary or text buffer, converts it into the proprietary object (such as CustomBundle), and hands it off to PixiJS. Once resolved, the CacheParser.test() function validates the object and getCacheableAssets() executes automatically.

Cache Invalidation and Cleanup

When an asset is unloaded via Assets.unload(keys), PixiJS queries the cache map created by getCacheableAssets(). If your parser properly mapped each alias and sub-resource, PixiJS ensures all linked entries are cleared from memory simultaneously, preventing memory leaks caused by lingering internal references.
