PixiJS Filter.defaultVertexSrc vs Custom Vertex Shaders

In PixiJS, filters rely on WebGL shaders to process display objects, utilizing either the built-in Filter.defaultVertexSrc or user-defined custom vertex logic. While Filter.defaultVertexSrc serves as a standard boilerplate for pass-through transformations and texture mapping, custom vertex logic allows developers to manipulate geometry, create positional deformations, and pass custom varying data directly to fragment shaders. This guide breaks down the core distinctions, operational mechanics, and appropriate use cases for both approaches.

Understanding Filter.defaultVertexSrc

Filter.defaultVertexSrc is the built-in GLSL vertex shader that PixiJS applies when no custom vertex code is provided. Its primary role is to set up standard coordinates for the fragment shader without altering the underlying geometry.

Under the hood, Filter.defaultVertexSrc:

  • Maps vertex attributes (aVertexPosition) to normalized device coordinates (NDC) using Pixi's internal projection matrix (uProjectionMatrix).
  • Calculates texture coordinates (vTextureCoord) using the filterMatrix uniform, aligning the filtered area correctly relative to the stage.
  • Normalizes coordinates so the fragment shader receives accurate mapping data across different screen resolutions and padding settings.

Because most standard 2D post-processing effects (such as color adjustments, blurs, blooms, and vignette effects) execute purely on the pixel level, Filter.defaultVertexSrc is typically sufficient.

Understanding Custom Vertex Logic

Custom vertex logic involves providing a custom GLSL string to the vertex parameter of a PIXI.Filter. Instead of relying on a simple flat pass-through, custom vertex shaders allow you to alter vertex positions before pixel rasterization occurs.

With custom vertex logic, you can:

  • Displace Vertices: Create wave, bend, skew, or flag-like wind animations by manipulating aVertexPosition using mathematical formulas (like sine or cosine waves) driven by a uniform time variable.
  • Generate Custom Varyings: Calculate per-vertex lighting, custom UV projections, or distance calculations in the vertex stage and pass them efficiently to the fragment shader via varying variables.
  • Optimize Computations: Move complex mathematical calculations out of the fragment shader (which runs per-pixel) and into the vertex shader (which runs per-vertex, typically only 4 times for a standard filter quad).

Key Differences

1. Geometry Manipulation vs. Pixel Processing

Filter.defaultVertexSrc treats the geometry as a static, flat rectangular quad. It does not alter vertex positions. Custom vertex logic allows programmatic alteration of the shape and position of the rendered quad on the GPU.

2. Matrix Management and Boilerplate

When using Filter.defaultVertexSrc, PixiJS automatically ensures uniforms like uProjectionMatrix and filterMatrix are bound and used properly. When writing custom vertex logic, you must correctly define and apply these matrices yourself to prevent projection errors, misplaced textures, or inverted rendering.

3. Complexity and Overhead

  • Default Vertex: Zero setup required. Developers only write the fragment shader.
  • Custom Vertex: Requires GLSL vertex programming knowledge, proper attribute declarations (aVertexPosition), and careful handling of texture coordinate generation to avoid breaking PixiJS resolution scaling and filter padding.

When to Use Which

Use Filter.defaultVertexSrc when:

  • Creating effects focused solely on color, transparency, pixel distortion, or lighting via fragment shaders.
  • Standard 2D filter operations (e.g., grayscale, tinting, drop shadows, pixelation).

Use Custom Vertex Logic when:

  • Creating mesh deformation effects, such as wave motion, page curls, or 3D-like perspectives.
  • Shifting computational load from the fragment shader to the vertex shader for performance optimization.
  • Passing custom geometric attributes or modified texture coordinates down the rendering pipeline.
