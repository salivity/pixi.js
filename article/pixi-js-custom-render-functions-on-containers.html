Pixi.js Custom Render Functions on Containers

In Pixi.js, overriding a Container's rendering behavior allows developers to execute low-level WebGL commands, alter rendering states, or inject custom logic directly into the display pipeline. This article explains how to intercept the render cycle by overriding the container's internal render methods, flush the active batch renderer, and properly manage child display objects.

Understanding the Container Render Cycle

When Pixi.js prepares a frame, the renderer traverses the display tree starting from the stage root. For every node, it updates transforms, applies masks or filters, and invokes the container's rendering logic. By default, a standard PIXI.Container does not draw anything itself; it simply iterates over its children.

To intercept this process, you override the rendering method on the container instance or create a subclass. In Pixi.js v7 and earlier, this internal hook is _render(renderer). In Pixi.js v8, the rendering architecture uses render(renderer).

Intercepting the Render Pipeline (Pixi.js v7)

To execute custom WebGL logic or intercept execution during the render pass, subclass PIXI.Container and override _render:

import * as PIXI from 'pixi.js';

class CustomRenderContainer extends PIXI.Container {
    _render(renderer) {
        // 1. Flush the batch renderer
        renderer.batch.flush();

        // 2. Intercept: Execute custom logic before children render
        this.preRenderCustomLogic(renderer);

        // 3. Render children using default behavior
        super._render(renderer);

        // 4. Flush again if children generated batched draws
        renderer.batch.flush();

        // 5. Intercept: Execute custom logic after children render
        this.postRenderCustomLogic(renderer);
    }

    preRenderCustomLogic(renderer) {
        const gl = renderer.gl;
        // Example: modify WebGL state or execute raw draw calls
    }

    postRenderCustomLogic(renderer) {
        const gl = renderer.gl;
        // Example: reset WebGL state or apply post-processing passes
    }
}

Key Considerations When Intercepting

1. Flushing the Batch Renderer

Pixi.js batches draw calls (such as sprites and graphics) to minimize WebGL state changes. If you execute native WebGL calls without flushing, your operations may execute out of order relative to the batched geometry. Calling renderer.batch.flush() forces Pixi.js to draw all queued elements up to that point.

2. Managing WebGL State

Pixi.js manages its own WebGL state via renderer.state. If your custom render logic changes native WebGL context parameters (such as gl.enable(gl.BLEND), gl.cullFace, or active shader programs), you must either:

  • Reset the state manually to its previous values.
  • Use renderer.state.set(...) and renderer.shader.bind(...) so Pixi's internal state tracker remains synchronized.

3. Modifying Child Traversal

Calling super._render(renderer) will draw the container's children automatically. If you want to conditionally skip rendering, sort children dynamically, or render specific children into custom Framebuffers, omit super._render(renderer) and manually iterate over the this.children array, calling child.render(renderer) as required.
