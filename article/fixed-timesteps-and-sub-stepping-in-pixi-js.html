Fixed Timesteps and Sub-Stepping in Pixi.js

Coupling a deterministic physics simulation with Pixi.js requires decoupling the variable rendering loop from the physics update cycle. While Pixi.js renders frames at fluctuating refresh rates via requestAnimationFrame, physics engines demand constant delta times and sub-stepping to maintain numerical stability and avoid tunneling. This guide explains how to implement the classic fixed timestep accumulator pattern, apply sub-stepping for high-velocity collisions, and interpolate transform states to ensure perfectly smooth rendering in Pixi.js without simulation jitter.

The Problem: Variable Refresh Rates vs. Deterministic Physics

Pixi.js drives its update loop using PIXI.Ticker, which provides a variable delta time based on the user's monitor refresh rate and device workload. Feeding variable delta times directly into a physics engine (such as Matter.js, Rapier, or Planck.js) introduces severe problems:

  • Non-deterministic behavior: Objects travel different distances depending on the user's frame rate.
  • Instability and explosion: A sudden frame drop spikes the delta time, causing collision solvers to push overlapping colliders apart with massive, unrealistic forces.
  • Tunneling: High-speed bodies pass through solid obstacles when the timestep is too large.

To resolve this, physics must step forward using a fixed time interval (\(dt\)), independent of the rendering frame rate.

The Accumulator Pattern

The accumulator pattern buffers the variable elapsed time provided by Pixi's ticker and consumes it in fixed, predictable slices.

  1. Measure elapsed time: Read the real-world time passed since the last frame.
  2. Clamp elapsed time: Cap the maximum delta time to prevent the "spiral of death," where the engine tries to catch up on a long lag spike by running dozens of expensive physics steps, causing an even longer lag spike on the next frame.
  3. Accumulate and consume: Add the clamped time to an accumulator variable. While the accumulator is greater than or equal to your fixed physics step (e.g., \(1/60\) of a second), advance the physics simulation by that fixed slice and subtract it from the accumulator.
const FIXED_STEP = 1 / 60; // 60 Hz physics step (in seconds)
const MAX_FRAME_TIME = 0.25; // Clamp delta to 250ms to prevent spiral of death

let accumulator = 0;

app.ticker.add((ticker) => {
    // Pixi ticker deltaMS is in milliseconds
    let frameTime = ticker.deltaMS / 1000;

    if (frameTime > MAX_FRAME_TIME) {
        frameTime = MAX_FRAME_TIME;
    }

    accumulator += frameTime;

    while (accumulator >= FIXED_STEP) {
        physicsWorld.step(FIXED_STEP);
        accumulator -= FIXED_STEP;
    }
});

Implementing Sub-Stepping

Sub-stepping breaks down a single fixed physics step into multiple smaller micro-steps. This is critical for complex constraint systems, fast-moving projectiles, and continuous collision detection.

Rather than running the entire engine at an extremely high rate (such as 240 Hz) in the main loop, you can divide your target step internally:

const FIXED_STEP = 1 / 60;
const SUB_STEPS = 4;
const SUB_STEP_TIME = FIXED_STEP / SUB_STEPS;

while (accumulator >= FIXED_STEP) {
    for (let i = 0; i < SUB_STEPS; i++) {
        physicsWorld.step(SUB_STEP_TIME);
    }
    accumulator -= FIXED_STEP;
}

Sub-stepping preserves overall simulation speed while giving constraints and collision solvers more iterations to resolve overlaps cleanly before rendering occurs.

Eliminating Visual Jitter with Interpolation

Because the physics clock rarely aligns perfectly with the display's vertical sync (VSync), the accumulator will usually contain a leftover fraction of time (accumulator < FIXED_STEP). If you directly assign the current physics body position to your Pixi.js display objects, the simulation will appear to stutter or jitter because the rendered frame does not match the actual point in time.

To achieve fluid motion, interpolate between each body's previous state and current state using the remaining accumulator time:

\[\alpha = \frac{\text{accumulator}}{\text{FIXED\_STEP}}\]

Here, \(\alpha\) represents how far the current render frame is between the previous physics state (\(0.0\)) and the current physics state (\(1.0\)).

Implementation Steps:

  1. Before running the physics update, record the body’s current position and rotation as its previous state.
  2. Run the fixed timestep loop to compute the current state.
  3. Calculate \(\alpha = \text{accumulator} / \text{FIXED\_STEP}\).
  4. For every rendered entity, blend the positions before Pixi renders the scene:
// Entity structure tracking previous and current physics transforms
class PhysicsSprite {
    constructor(sprite, body) {
        this.sprite = sprite;
        this.body = body;
        this.prevX = body.position.x;
        this.prevY = body.position.y;
        this.prevRotation = body.angle;
    }

    saveState() {
        this.prevX = this.body.position.x;
        this.prevY = this.body.position.y;
        this.prevRotation = this.body.angle;
    }

    interpolate(alpha) {
        this.sprite.x = this.prevX + (this.body.position.x - this.prevX) * alpha;
        this.sprite.y = this.prevY + (this.body.position.y - this.prevY) * alpha;
        this.sprite.rotation = this.prevRotation + (this.body.angle - this.prevRotation) * alpha;
    }
}

The Combined Pixi.js Ticker Loop:

const entities = []; // Array of PhysicsSprite instances

app.ticker.add((ticker) => {
    let frameTime = ticker.deltaMS / 1000;
    if (frameTime > 0.25) frameTime = 0.25;

    accumulator += frameTime;

    while (accumulator >= FIXED_STEP) {
        // Save current positions as previous before advancing
        for (const entity of entities) {
            entity.saveState();
        }

        // Advance physics
        physicsWorld.step(FIXED_STEP);

        accumulator -= FIXED_STEP;
    }

    // Calculate alpha for the leftover time
    const alpha = accumulator / FIXED_STEP;

    // Update Pixi sprite transforms based on the interpolated state
    for (const entity of entities) {
        entity.interpolate(alpha);
    }
});

This decoupled architecture guarantees that physics simulations remain deterministic across all hardware configurations while visual output remains lock-step smooth across 60 Hz, 120 Hz, 144 Hz, and variable refresh rate (VRR) displays.
