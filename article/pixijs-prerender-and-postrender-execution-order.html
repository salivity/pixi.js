PixiJS Prerender and Postrender Execution Order

Pixi.js uses a recursive, depth-first traversal to draw its scene graph, which directly dictates the sequence in which prerender and postrender events are dispatched. Understanding this execution order is critical for synchronizing custom WebGL/WebGPU calls, updating transforms, and managing canvas states during rendering. This article breaks down the exact execution flow of both the renderer-level and container-level lifecycle events across a nested scene graph hierarchy.

The Traversal Model

Pixi.js renders display objects hierarchically starting from the root stage. Because rendering relies on standard depth-first search (DFS) recursion, the events execute as follows:

  • prerender follows pre-order traversal (top-down): A parent container emits prerender before its children are processed.
  • postrender follows post-order traversal (bottom-up): A parent container emits postrender only after all of its children have completed their rendering cycles.

Complete Lifecycle Sequence

When rendering a frame via renderer.render(stage), Pixi.js executes events in a strict sequence encompassing both the renderer instance and the display tree containers.

Example Scene Graph

Consider the following nested structure:

Renderer
└── Stage (Root)
    └── Container A
        ├── Sprite 1
        └── Sprite 2

Order of Execution

  1. Renderer: prerender
    The renderer begins the frame, binds the main render target, and clears buffers.
  2. Stage: prerender
    The root container initiates its render pass.
  3. Container A: prerender
    Container A enters the pipeline before drawing any nested elements.
  4. Sprite 1: prerender
    The first leaf node prepares to draw.
  5. Sprite 1: postrender
    The first leaf node finishes rendering its geometry and textures.
  6. Sprite 2: prerender
    The sibling leaf node prepares to draw.
  7. Sprite 2: postrender
    The sibling leaf node finishes rendering.
  8. Container A: postrender
    Container A resolves after all its descendants have rendered.
  9. Stage: postrender
    The root container completes its render cycle.
  10. Renderer: postrender
    The frame is finalized, buffers are flushed, and control is returned to the main loop.

Key Takeaways for Developers

  • Transform Updates: If you need to read or alter a child object's world transform or shader uniform right before it renders, use that specific child's prerender event. Listening to the parent's prerender occurs before child transforms are recursively updated.
  • State Clean-Up: Custom blend modes, stencil buffer masks, or bound framebuffers applied during prerender should be restored in the corresponding object's postrender event to avoid leaking visual state to subsequent sibling or parent draws.
  • Performance Impact: Attaching prerender and postrender listeners to hundreds of leaf nodes introduces event-dispatch overhead. For performance-sensitive operations, listen at a shared higher-level Container or use custom render methods.
