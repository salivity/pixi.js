How Pixi.js Handles Compressed Textures: ASTC, ETC2, BCn

Pixi.js handles platform-specific compressed textures by leveraging modern WebGL extensions through its internal asset loading pipeline. By detecting the target device's hardware capabilities at runtime, Pixi.js selects the most efficient texture format available—such as ASTC for modern mobile, ETC2 for broader Android support, or BCn/S3TC for desktop platforms—and passes the compressed data directly to the GPU to drastically minimize VRAM usage and eliminate decompression overhead.

Hardware Capability Detection

Before loading or rendering compressed textures, Pixi.js queries the WebGL rendering context (WebGLRenderingContext or WebGL2RenderingContext) for supported hardware compression extensions. Modern versions of Pixi.js inspect the presence of specific extensions, including:

  • WEBGL_compressed_texture_astc: Adaptive Scalable Texture Compression (ASTC), standard across modern iOS devices (A8 chip and later) and modern Android hardware.
  • WEBGL_compressed_texture_etc: Ericsson Texture Compression (ETC2/EAC), the default standard for Android devices supporting OpenGL ES 3.0.
  • WEBGL_compressed_texture_s3tc and WEBGL_compressed_texture_bptc: S3TC (DXT1/DXT5) and BPTC (BC7), standard across desktop GPUs (NVIDIA, AMD, Intel).
  • WEBGL_compressed_texture_pvrtc: Legacy format primarily supported on older PowerVR-based iOS devices.

Container Parsing via the Assets Pipeline

Pixi.js does not read raw block-compressed bitstreams directly without metadata. Instead, it relies on container formats loaded through its @pixi/assets package. The supported container formats include:

  • KTX / KTX2 (.ktx, .ktx2): The standard Khronos texture container. KTX files wrap raw ASTC, ETC, or BCn payloads with the necessary GL internal format headers.
  • DDS (.dds): Primarily used for desktop BCn/S3TC textures.

Parsers registered within the asset loader read the container headers to identify mipmap levels, byte offsets, pixel dimensions, and the internal GL format constant (such as COMPRESSED_RGBA_ASTC_4x4_KHR or COMPRESSED_RGBA_S3TC_DXT5_EXT).

Dynamic Format Resolution and Fallbacks

In production environments, developers rarely serve a single compressed texture format. Pixi.js supports manifest-based asset management that allows developers to define multiple variants of the same sprite or spritesheet:

import { Assets } from 'pixi.js';

// Pixi automatically prioritizes formats based on device support
await Assets.load([
    'spritesheet.astc.ktx',
    'spritesheet.etc2.ktx',
    'spritesheet.bc7.dds',
    'spritesheet.png' // Fallback
]);

During resolution, Pixi.js compares the available file extensions against the detected WebGL extension priority list. If a platform lacks hardware support for ASTC, Pixi skips the .astc.ktx asset and attempts to load an ETC2, BCn, or uncompressed PNG/WebP fallback, preventing rendering errors.

Basis Universal and Transcoding

Pixi.js also provides integration with Basis Universal through KTX2 wrappers. Instead of requiring developers to pre-encode textures into distinct ASTC, ETC2, and BCn files, Basis Universal files store textures in an intermediate format (ETC1S or UASTC). At runtime, a WebAssembly (WASM) transcoder detects the active platform's capabilities and converts the intermediate data into native ASTC, ETC2, or BCn blocks on the fly before GPU upload.

Direct GPU Uploading

When uploading regular textures (like PNG or JPEG), the browser decomputes the file into raw RGBA8888 bitmap data in system memory before calling gl.texImage2D. This increases CPU memory usage and can cause frame drops.

When handling compressed textures, Pixi.js bypasses image decoding. It extracts the raw binary payload from the container and invokes gl.compressedTexImage2D directly. The data remains block-compressed in VRAM, resulting in up to a 75% reduction in texture memory footprint and faster rendering performance on target devices.
