PixiJS Event Priority for Overlapping Elements

When multiple interactive display objects overlap in Pixi.js and share an identical zIndex, Pixi.js resolves event priority using the scene graph’s display list order. By default, the hit-testing system evaluates elements from front to back according to their rendering sequence, giving top priority to the element that was rendered last. This article explains the internal mechanisms Pixi.js uses to determine hit-testing order, how child array indexing influences event dispatch, and how parent-child container structures affect interaction resolution.

The Scene Graph and Children Array Order

In Pixi.js, the visual stack and hit-test stack are directly derived from the order of display objects in their parent container’s children array. When elements have the same zIndex (or when sortableChildren is disabled), Pixi.js does not re-sort the display list based on depth.

Instead, it preserves insertion order:

  • An element added first (container.addChild(elementA)) occupies index 0.
  • An element added subsequently (container.addChild(elementB)) occupies index 1.

During the render pass, elements are drawn sequentially from index 0 upward. Consequently, higher-indexed siblings are drawn over lower-indexed siblings, placing the highest-indexed sibling visually on top.

How the EventBoundary Resolves Hits

Pixi.js delegates hit testing to its event system via the EventBoundary class. To ensure that clicks and pointer interactions match what the user sees on screen, EventBoundary performs hit testing in the exact reverse of the rendering order.

When processing pointer interactions:

  1. Reverse Traversal: The EventBoundary traverses the display hierarchy recursively from top to bottom.
  2. Sibling Evaluation: Within any given container, siblings are evaluated starting from the highest index in the children array down to index 0.
  3. Hit Test Detection: Pixi.js tests the pointer's coordinates against each child's hit area or geometry using containsPoint.
  4. Target Acquisition: The first eligible interactive element (an object with an active eventMode such as 'static' or 'dynamic') that returns true for containsPoint becomes the primary target.

Because evaluation begins at the highest index, the element that was added last—and therefore rendered on top—captures the interaction first.

Nested Hierarchies and Depth-First Search

When overlapping objects are nested within different parent containers, container order takes precedence over child order. The EventBoundary uses a depth-first search approach:

  • Containers higher up in the root display list are searched before containers lower down.
  • All children inside the top-most container are evaluated before Pixi.js falls back to evaluating siblings of that container.
  • If Container B is rendered on top of Container A, every interactive child inside Container B will receive hit priority over any child in Container A, regardless of the individual zIndex values or array positions of the children within their respective parents.

Event Propagation and Interception

Once the top-most element is identified as the target, Pixi.js dispatches the interaction event. By default, events bubble up through the scene graph to parent containers. However, sibling elements underneath the target do not automatically receive the event.

If the top-most element needs to pass interactions through to the elements beneath it, its eventMode can be set to 'passive' or 'none', which removes it from hit-testing consideration entirely. Alternatively, setting eventMode = 'none' allows hit tests to ignore the visual overlay and reach underlying siblings at lower array indices.
