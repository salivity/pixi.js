Pixi.js Tree Mutation During Active Render Pass

This article explores how Pixi.js processes scene graph modifications executed during an active render pass, detailing the internal traversal mechanics, the risks of mid-render mutations, and how modern versions manage rendering state. Pixi.js prioritizes runtime performance over mutation resilience during draw calls, meaning modifying the display tree mid-traversal can result in index shifting, desynchronized matrix calculations, or pipeline errors.

Direct Traversal and Garbage Collection Avoidance

When renderer.render(stage) is invoked, Pixi.js traverses the display hierarchy (containers and their child elements) to compute transforms and dispatch WebGL or WebGPU draw instructions. To maintain high frame rates and avoid triggering garbage collection, Pixi.js does not defensively clone the children array of a container prior to iteration. Instead, the renderer loops directly over the live reference of each container's child list.

If a script modifies the tree—such as by calling addChild, removeChild, or reordering elements from within a custom render callback or WebGL hook—the underlying array changes mid-loop. Removing an element shifts subsequent sibling indices backward, which typically causes the traversal loop to skip the adjacent child for that frame. Conversely, adding an element can either cause duplicate processing of existing elements or inadvertently process the newly added element before its transform matrices are properly initialized.

Transform Pipeline Desynchronization

Before rendering display objects, Pixi.js requires up-to-date world transforms, alpha values, and render bounds. Under normal execution, transform propagation flows strictly top-down: parent transforms update before child transforms.

Modifying parent-child relationships while a render pass is underway breaks this propagation chain. If a display object is detached and re-parented during rendering, it may inherit stale matrix data from its previous ancestor or draw with uncalculated transforms. This leads to visual artifacts such as elements flickering, jumping to (0,0), or drawing with incorrect scaling for a single frame.

RenderGroups and Instruction Lists in Pixi.js v8

In Pixi.js v8, rendering architecture shifted toward a reactive model utilizing RenderGroup structures and pre-compiled render instruction pipelines. In this architecture, display tree structures are compiled into flattened command lists to maximize batching and modern graphics API efficiency.

Mutating the display tree during the active render pass in v8 causes severe desynchronization:

  1. Instruction List Invalidation: The instruction list built for the current frame no longer matches the current state of the scene graph.
  2. Dirty Flag Latency: Modern Pixi.js relies on dirty flags (_didChangeId) to invalidate caches. When changes occur in the middle of instruction execution, the engine cannot safely rebuild the instruction list mid-frame, potentially throwing runtime exceptions or dereferencing null pointers.

Safe Display Tree Modification

Standard Pixi.js application lifecycles decouple scene updates from rendering. The PIXI.Ticker mechanism runs update callbacks sequentially before calling the renderer:

Ticker Event -> Update Systems / Game Logic -> Transform Propagation -> Render Pass

To avoid tree mutation during rendering:

  • Defer Mutations: If a custom render function or graphics callback requires a scene change, queue the action to execute in the next tick via ticker.addOnce() or a microtask (queueMicrotask()).
  • Use Visibility Toggles: Instead of removing elements during render callbacks, toggle renderable = false or visible = false. These flags are read dynamically during the pass and do not alter array lengths or memory layouts.
