Pixi.js Kawase Blur vs Gaussian Blur Performance

In Pixi.js, applying blur effects in real time presents an ongoing trade-off between rendering speed and visual fidelity. While the standard GaussianBlurFilter offers mathematically accurate, ultra-smooth blurs, its heavy computational cost can rapidly cause frame rate drops, especially on mobile devices. In contrast, the KawaseBlurFilter—available via the @pixi/filter-kawase-blur package—uses an iterative sampling technique that delivers visually comparable results with substantially higher rendering performance. This comparison breaks down how both filters operate under the hood, how their performance differs, and how to choose the right one for your application.

The Architectural Difference

The standard GaussianBlurFilter operates using a classic two-pass separable Gaussian kernel: one horizontal pass and one vertical pass. To achieve a smooth blur across a wide radius, the shader must sample numerous surrounding pixels for every fragment on the screen. As the blur strength increases, the number of texture lookups per pixel grows significantly. This creates a severe memory bandwidth bottleneck and places high demand on the GPU’s fill rate.

The KawaseBlurFilter, based on the blur algorithm developed by Masaki Kawase, takes an iterative approach. Instead of calculating a wide kernel in single passes, it executes multiple lightweight passes (iterations), slightly increasing the sample offset with each pass. Each iteration samples only a fixed number of points (typically four diagonally offset texture reads). Because the number of texture samples per pass is minimal, the GPU handles the workload far more efficiently, even when creating large, diffuse blurs.

Performance Breakdown

  1. Texture Sampling and Bandwidth: A large-radius Gaussian blur requires dozens of texture samples per pixel across both axes. The Kawase blur achieves an equivalent spread using 3 to 5 iterations with only 4 taps per iteration. This drastically reduces the total number of texture fetches, lowering GPU memory bandwidth pressure.

  2. Fill-Rate Sensitivity: Because GaussianBlurFilter performs more arithmetic and texture fetching per fragment, high-resolution screens (such as 4K displays or high-DPI mobile screens) experience sharp frame drops. KawaseBlurFilter executes faster fragment programs, making it significantly less prone to fill-rate bottlenecks on Retina and mobile displays.

  3. Frame-Time Scaling: At low blur values (1 to 3 pixels), the performance difference between the two filters is negligible. However, as the blur radius expands to medium or large values, KawaseBlurFilter consistently maintains 60 frames per second, whereas GaussianBlurFilter frame times scale poorly and can degrade real-time animations. Benchmarks commonly show Kawase blur running 2x to 4x faster than Gaussian blur at moderate to high strengths.

Visual Quality Comparison

The trade-off for Kawase's speed is a minor deviation in mathematical precision.

  • GaussianBlurFilter yields true, continuous diffusion with no directional bias or edge artifacts, making it the superior choice for high-fidelity graphic design or subtle depth-of-field effects.
  • KawaseBlurFilter can occasionally produce subtle diamond-shaped or boxy sampling patterns if configured with too few iterations over an excessively large radius. However, by fine-tuning the kernels or passes properties, these artifacts become imperceptible to the human eye during active gameplay or motion.

When to Use Each Filter

Use KawaseBlurFilter when:

  • You are animating the blur radius or applying blur to moving scene elements in real time.
  • Your target audience includes mobile browsers or low-powered hardware.
  • You are building dynamic UI backdrops, such as frosted glass effects.
  • Blur radii are medium to large.

Use GaussianBlurFilter when:

  • You only need a very small blur radius (1 to 2 pixels) where the sampling overhead is negligible.
  • The blurred display object is static and can be cached using cacheAsBitmap = true.
  • Perfect mathematical accuracy is required and dynamic frame rates are not a priority.
