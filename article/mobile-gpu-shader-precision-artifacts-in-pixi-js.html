Mobile GPU Shader Precision Artifacts in Pixi.js

Rendering procedural noise in Pixi.js often yields crisp, detailed visuals on desktop systems but breaks down into blocky, banded, or jittery artifacts on mobile devices. This discrepancy stems primarily from hardware-enforced floating-point precision differences between desktop and mobile graphics chipsets. This guide examines the technical causes behind these precision artifacts—including GLSL precision qualifiers, floating-point mantissa limits, coordinate scaling, and algorithmic instability—and outlines the standard approaches to resolve them.

Floating-Point Precision: mediump vs. highp

The primary cause of shader artifacts on mobile devices is the difference in floating-point precision implementations:

  • Desktop GPUs: Modern desktop GPUs typically process all floating-point math in full 32-bit single precision (highp), even if a GLSL shader specifies mediump or lowp. The hardware ignores lower-precision declarations because it has dedicated 32-bit execution units.
  • Mobile GPUs: Mobile chipsets (such as ARM Mali, Qualcomm Adreno, and PowerVR) are heavily optimized for battery efficiency and silicon area. When a shader declares precision mediump float;, mobile hardware executes operations using true 16-bit half-precision floats (fp16).

In 16-bit floating-point format, only 10 bits are allocated to the mantissa (fractional component). This provides roughly 3 to 4 decimal digits of precision. When computing procedural noise—which requires subtle mathematical variations across tiny spatial increments—10 bits of precision are quickly exhausted, causing truncation, quantization, and stair-step banding.

High-Frequency Hash and Sine Instability

Most basic noise shaders rely on pseudo-random hash functions utilizing high-frequency trigonometry, such as:

float hash(vec2 p) {
    return fract(sin(dot(p, vec2(12.9898, 78.233))) * 43758.5453);
}

This classic one-liner depends entirely on high precision. Multiplying by a large scalar like 43758.5453 pushes values into a range where a 16-bit float loses all fractional data. Additionally, trigonometric functions like sin() on mobile architectures have lower internal accuracy in mediump. Combined with the loss of significant digits, the pseudo-random distribution collapses, manifesting as concentric circles, static lines, or complete loss of noise detail.

Accumulating Uniforms and Coordinate Scaling

Precision degradation worsens when handling scale and time:

  • Unnormalized Coordinates: If you pass screen-space pixel coordinates (e.g., gl_FragCoord.xy or values from Pixi.js filters ranging from 0 to 2048) into the noise function, values at the bottom-right of the screen lose precision significantly faster than those near the origin (0, 0).
  • Accumulating Time Uniforms: Supplying a continuously increasing timestamp (e.g., passing performance.now() directly to a uTime uniform) causes numbers to grow indefinitely. As the integer magnitude increases, floating-point formats drop fractional precision to compensate, causing animated noise to stutter and eventually freeze.

How to Fix Precision Artifacts in Pixi.js

1. Enforce highp Precision in the Fragment Shader

Explicitly declare high precision at the top of your custom Pixi.js fragment shader:

precision highp float;

While highp is standard in WebGL 2, verify WebGL 1 support on older targets using the OES_fragment_precision_high extension. Pixi.js automatically manages precision headers in standard filter setups, but custom fragment shaders must not default to mediump.

2. Normalize Input Coordinates

Transform screen coordinates into normalized device-like coordinates (ranging from 0.0 to 1.0) on the CPU or in the vertex shader before passing them to the noise algorithm. This keeps the input values within the range where floating-point density is highest.

3. Wrap Time Variables

Prevent uniform values from expanding indefinitely. Modulo the time variable on the CPU inside the Pixi.js ticker before uploading it to the GPU:

app.ticker.add((delta) => {
    // Loop time within a defined interval rather than letting it grow infinitely
    customFilter.uniforms.uTime = (performance.now() / 1000) % 3600;
});

4. Use Low-Precision-Safe Noise Algorithms

Replace sine-based pseudo-random hashes with bit-manipulation hashes (in WebGL 2 / GLSL 300 es) or gradient-based noise algorithms like Simplex noise. Simplex and Perlin noise avoid the massive multipliers found in older pseudo-random functions and behave more predictably on lower-precision mobile hardware.
