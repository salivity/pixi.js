Sharing a PixiJS BitmapFont Without Texture Overhead

Rendering hundreds of dynamic text labels in Pixi.js can severely degrade performance if each label creates its own texture. By generating or loading a single BitmapFont and referencing it across multiple BitmapText instances, you can display hundreds of UI elements simultaneously while sharing a single underlying texture atlas. This approach eliminates redundant GPU memory consumption, minimizes texture swaps, and allows Pixi.js to batch all text rendering into minimal draw calls.

Register a Single BitmapFont Instance

To avoid texture overhead, ensure the font texture atlas is created exactly once during initialization. Pixi.js allows you to load an external bitmap font (consisting of an image and an XML or JSON descriptor) or generate one procedurally at runtime using an existing system or web font.

Option A: Loading via Pixi Assets

When loading pre-baked bitmap fonts created with tools like BMFont or ShoeBox, load the descriptor file once through the Assets manager:

import { Assets } from 'pixi.js';

// Load once during game or UI preloading
await Assets.load('assets/fonts/ui-font.xml');

Pixi automatically parses the XML/JSON file and registers the font globally under the name defined inside the file.

Option B: Generating at Runtime

If you prefer runtime generation without external files, generate the BitmapFont using BitmapFont.from:

import { BitmapFont } from 'pixi.js';

BitmapFont.from('SharedUIFont', {
    fontFamily: 'Arial',
    fontSize: 32,
    fill: '#ffffff',
}, {
    chars: BitmapFont.ALPHANUMERIC,
    resolution: window.devicePixelRatio || 1,
});

Call this initialization function once during startup. Calling BitmapFont.from inside UI creation loops will generate a new texture per call, causing memory leaks and performance drops.

Reusing the Font Across Multiple Labels

Once registered, instantiate labels using the BitmapText class. Reference the registered font by name within the text style configuration.

import { Container, BitmapText } from 'pixi.js';

const uiContainer = new Container();

for (let i = 0; i < 500; i++) {
    const label = new BitmapText({
        text: `Item ${i}`,
        style: {
            fontName: 'SharedUIFont',
            fontSize: 24, // Scales glyphs geometrically without creating new textures
        },
    });

    label.position.set((i % 10) * 80, Math.floor(i / 10) * 30);
    uiContainer.addChild(label);
}

Every BitmapText object created this way functions as an internal batch of sprite quads that point directly to coordinates on the single shared font texture atlas.

Preventing Redundant Textures and Draw Calls

To ensure hundreds of labels operate with the lowest possible overhead, follow these core practices:

  • Rely on Geometric Scaling: Adjusting the fontSize property on a BitmapText scales the existing quad coordinates relative to the base font size. It does not re-rasterize the font or create a new texture.
  • Use Tinting for Color Variations: Instead of creating separate bitmap fonts for different colors, generate the base font in pure white (#ffffff). You can then apply the tint property to individual BitmapText instances (e.g., label.tint = 0xff0000 for red), which is handled entirely within the fragment shader at no texture cost.
  • Keep Text on the Same Render Layer: Pixi's batch renderer can draw all characters from all labels in a single draw call as long as other objects with different textures are not interleaved between them. Group UI text within the same container or contiguous z-indices to preserve draw call batching.
  • Limit Dynamic Character Sets: When using runtime font generation, define the chars array with only the necessary characters to keep the underlying texture atlas as small as possible.
