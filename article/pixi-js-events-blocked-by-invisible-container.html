PixiJS Events Blocked by Invisible Container

When an invisible container overlays the stage in Pixi.js, it frequently intercepts and terminates pointer interactions meant for underlying display objects. This issue stems from Pixi.js's top-down hit-testing pipeline, where invisible or fully transparent objects still participate in pointer detection if their interaction settings or hit areas remain active. Understanding how Pixi.js processes pointer events, transparency, and container hierarchies provides a straightforward path to resolving these event conflicts.

The Scene Graph and Hit Testing

Pixi.js processes pointer events (such as pointerdown, pointerup, and pointermove) by traversing the scene graph in reverse order—from top to bottom, matching the visual rendering stack. During this hit-testing phase, the interaction system queries display objects to determine if the pointer coordinates fall within their bounds. The topmost interactive object that confirms a hit absorbs the event. If an overlay container sits above other objects in the display list, the engine checks it first, preventing the event from reaching elements beneath it.

Alpha Versus Visibility

A frequent cause of "invisible" containers blocking events is the use of alpha = 0 instead of visible = false.

  • alpha = 0: Renders the object completely transparent, but the object remains in the scene graph's interactive tree. If eventMode (or interactive in older versions) is enabled, or if it contains interactive children, it will still evaluate coordinates and capture pointer events.
  • visible = false: Removes the object and its children from both rendering and hit testing entirely.

If a developer hides a container using alpha = 0 to fade it out or keep its layout calculated, Pixi.js treats that container as fully capable of capturing user input unless interaction is explicitly disabled.

Explicit Hit Areas and Bounding Boxes

Containers do not possess intrinsic widths or heights; their boundaries are determined by their children. However, developers often assign an explicit hitArea (such as a PIXI.Rectangle) to a container for touch detection or layout management.

When a container has an active hitArea, Pixi.js performs a geometric check against that shape. Even if the container has no visible graphics or textures rendered inside it, an active hitArea covers the specified region like a pane of glass, capturing all incoming pointer events before they can reach the stage elements below.

The Role of interactiveChildren and eventMode

In Pixi.js v7 and v8, interaction is governed by eventMode (replacing the legacy interactive = true/false flag):

  • eventMode = 'none': The object completely ignores hit testing and does not block events.
  • eventMode = 'passive': The object does not emit events itself, but allows interaction on its children.
  • eventMode = 'static' or 'dynamic': The object actively intercepts hit tests and stops them from passing through to layers underneath.

Furthermore, containers have an interactiveChildren property, which defaults to true. Even if the overlay container itself does not capture events, any interactive child within it—even transparent ones—will capture events across their respective areas.

How to Prevent Invisible Containers from Blocking Events

To restore interactivity to underlying stage elements, adjust how the overlay container handles hit testing:

  1. Disable interaction on the overlay: Set container.eventMode = 'none' (or container.interactive = false in Pixi.js v6 and earlier). This instructs the hit-test algorithm to bypass the container and all of its contents.
  2. Disable child interaction: If the container must remain in the display tree, set container.interactiveChildren = false to prevent child elements from intercepting clicks.
  3. Toggle visibility instead of transparency: If the overlay should not be seen or touched, set container.visible = false instead of altering its alpha.
  4. Remove the hit area: If a temporary hitArea was assigned to the overlay, set container.hitArea = null when the overlay is idle so pointer events fall through to the stage below.
