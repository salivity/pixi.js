Pixi.js Ticker Priority Execution Order Explained

This article breaks down the exact execution order of Pixi.js Ticker priorities, outlining how the internal queue arranges update tasks from start to finish. In Pixi.js, the Ticker system controls the main update loop, invoking registered listener callbacks on every frame based on their assigned priority values. By understanding these predefined constants and internal tie-breaking mechanisms, developers can prevent frame lag, eliminate input-to-render race conditions, and ensure systems update in the correct sequence.

The Core Rule: Descending Numerical Order

Pixi.js schedules Ticker listeners in strictly descending numerical order. The higher the priority number, the earlier the task executes in the frame update loop.

When you register a listener using ticker.add(fn, context, priority), the optional priority parameter defaults to 0 (PIXI.UPDATE_PRIORITY.NORMAL). Listeners assigned positive integers run before the default tasks, while listeners assigned negative integers run after.

Standard Execution Order of Predefined Priorities

Pixi.js provides predefined constants under the PIXI.UPDATE_PRIORITY enumeration. The execution cycle progresses down the queue in the following exact sequence:

  1. Custom High Priorities (> 50): Any custom integer higher than 50 executes first.
  2. UPDATE_PRIORITY.INTERACTION (50): Pixi's interaction and event management systems run here to process pointer, touch, and user inputs before game logic processes them.
  3. UPDATE_PRIORITY.HIGH (25): Critical game logic that depends on fresh input but must run before normal world updates.
  4. UPDATE_PRIORITY.NORMAL (0): The default priority level. This is where standard animation updates, movement logic, and general application tasks are processed.
  5. UPDATE_PRIORITY.LOW (-25): Post-processing game state updates, such as physics resolution reconciliation or camera positioning that needs all object transforms finalized.
  6. UPDATE_PRIORITY.UTILITY (-50): Background operations, garbage cleanups, external telemetry, or low-priority maintenance tasks that execute after gameplay updates.
  7. Custom Low Priorities (< -50): Any custom negative integers lower than -50 run last in the frame.

Tie-Breaking Identical Priorities (FIFO)

When two or more listeners share the exact same priority value, the Ticker resolves the order using First-In, First-Out (FIFO) logic.

The internal queue uses a linked list structure to manage listeners. When a new listener is added with a priority identical to an existing listener, the new listener is placed directly after the existing ones at that same priority level. Consequently, tasks with the same priority value will always execute in the exact order they were registered.

Render Phase Execution

The rendering step itself is managed through the Ticker. In a standard PIXI.Application setup, the application automatically registers its render task to the shared Ticker at UPDATE_PRIORITY.LOW (-25).

Because rendering occurs at -25, any code placed in NORMAL (0) or HIGH (25) is guaranteed to finish computing positions, scales, and state changes before Pixi draws the stage to the canvas. Tasks assigned to UTILITY (-50) will run after the scene has already rendered to the screen.
